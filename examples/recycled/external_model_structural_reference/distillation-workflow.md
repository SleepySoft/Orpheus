# 双 Runtime 模型蒸馏工作流

本模型禁止从生成 C 代码直接画完整 Orpheus 图。直接转换会保留函数名和若干音频数组，却容易丢掉跨 TID 缓冲、并行支路、反馈、运行期参数事务、跨 Runtime 数组状态和更新顺序。

当前唯一进度入口是 [distillation-index.yaml](distillation-index.yaml)。结构参考和局部图只能作为证据附件，不能反向代表模块已经蒸馏完成。

## 进度字段

每个模块分别记录六项进度：

| 字段 | 要回答的问题 |
|---|---|
| `boundary` | 输入、输出、shape、单位和通道语义是否确定？ |
| `schedule` | 属于哪个 TID，何时读写状态，与其他 TID 如何交换？ |
| `algorithm` | 公式、分支、反馈、饱和和边界条件是否还原？ |
| `state` | delay、ring buffer、ramper、sequence、reset 等状态是否完整？ |
| `parameters` | TOP/RTC 字段、默认值、更新策略和系数布局是否提取并校验？ |
| `golden` | 是否用参考实现输出验证了正常、边界、状态迁移和重置？ |

`artifact` 只表示已有笔记、组件或局部图，不表示上述六项已完成。只有六项全部为 `verified`，`system_graph_eligible` 才能为 `true`。

## 单模块步骤

1. **锁定证据**：核对索引中的源文件 SHA-256；TOP 通配文件在分析该模块时逐文件补 hash。
2. **确定边界**：从调用者和被调用者双向确认 shape、通道顺序、单位和所有旁路，不能只看函数签名。
3. **还原调度与状态**：记录 TID、读写缓冲、初值、reset/disable/shutdown 和跨帧更新顺序。
4. **还原算法**：将生成代码写成公式、状态机或伪代码；并行路径、反馈和分支必须显式保留。
5. **提取参数**：用脚本读取 TOP/接口配置，产物带 shape、来源字段和 SHA-256，不手抄长数组。
6. **选择实现**：优先组合已有通用组件；只有无法表达且有完整证据的独特算法才新增 C 组件。
7. **建立 golden**：至少覆盖默认、非零控制、极值、跨块状态、reset 和 bypass；数值容差须写明来源。
8. **发布独立切片**：先形成可单独运行的目录工程，节点说明重点解释用途和为什么这样连接。
9. **进入完整图**：只有索引门禁通过后，才允许在系统工程中替换对应占位边界。

## 记录约定

- 模块 ID 稳定，不随最终组件名变化；代码、文档、测试和提交信息都引用该 ID。
- 源代码符号只放在模块分析记录的“证据”段，不把外部命名传播到组件 ID 或 UI。
- 结构推断写成 `hypothesis`，必须附能证伪它的检查；未经验证不得升级为算法事实。
- 通用组件近似必须标记 `approximation`，不能因为图可运行就称为蒸馏完成。
- 每完成一个模块，同一提交中更新索引、分析记录、提取脚本、golden 和独立切片。

## 组装顺序

先完成调度和双向总线，再做 Runtime A 的输入/Big6/后处理；随后完成 2→6 空间分解与 13→22 混音；最后处理多速率自适应响度和 Runtime B。该顺序让每一步都有可观测输入输出，同时避免在跨核协议尚未明确时提前画闭环。
