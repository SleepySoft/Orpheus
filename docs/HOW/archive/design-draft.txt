可视化音频组件框架开发指导文档
文档目的

本文用于指导开发 Agent 对可视化音频组件框架进行需求分析、任务拆分、实现、测试和交付。

Agent 应遵循以下原则：

先定义稳定的数据契约和接口，再实现 UI 与运行功能。
按可独立验证的子系统拆分任务。
每个阶段必须形成可运行闭环。
实时路径由 C/C++ 实现。
Python 负责工程编排、构建、验证和代码生成。
UI 只通过统一控制接口访问运行实例。
PC 仿真与目标部署使用相同的工程模型、组件定义和控制语义。
生成代码以复制组件源码、生成实例和连接代码为主。
每项任务必须提供测试、文档和验收结果。
未冻结上层契约前，不并行开发依赖该契约的子系统。
1. 原始需求
1.1 产品目标

开发一套面向音频 DSP 学习、算法实验、PC 实时处理和嵌入式部署的可视化组件框架。

用户通过图形界面添加组件、连接端口、配置参数和组织子系统。工程可以在 PC 上动态编译和运行，也可以生成完整、可读、可编译的 C/C++ 工程。

框架应覆盖以下使用流程：

创建音频工程。
添加和连接 DSP 组件。
配置采样率、块长度、通道数和任务。
在 PC 上编译组件并运行工程。
为每一路输入注入音频。
监听任意输出或中间信号。
修改运行参数并获取反馈。
添加波形、频谱、性能和内存探针。
连接正式部署目标并进行在线调试。
生成完整 C/C++ 工程或静态库。
对 PC 结果与生成代码结果进行一致性验证。

1.3 组件化需求

每个基础组件必须满足：

2. 技术选型
2.1 总体技术栈
图形界面：TypeScript + React + React Flow
桌面容器：Tauri
工程编排：Python 3.12+
运行时：C++20
组件接口：C ABI
组件实现：C11 或 C++20
构建系统：CMake + Ninja
工程描述：YAML
运行计划：JSON 或二进制中间表示
控制协议：自定义消息模型
音频后端：JUCE 或 miniaudio
测试：GoogleTest + pytest
数据校验：JSON Schema
文档：Markdown

2.2 图形界面

选择 TypeScript、React 和 React Flow。

React Flow 提供自定义节点、多端口、连线、缩放、选择、MiniMap、分组和嵌套子图支持，适合作为图编辑表现层。

UI 层负责：

图形编辑。
参数展示。
用户交互。
运行状态展示。
教学内容展示。
Probe 数据可视化。

UI 层不负责：

DSP 图调度。
端口语义推导。
组件动态加载。
实时代码执行。
目标通信细节。

Rete.js 可作为视觉编程框架的设计参考，其类型化节点、数据流和控制流模型具有参考价值。核心实现采用独立领域模型，避免前端框架决定 DSP 执行语义。

2.3 桌面应用容器

选择 Tauri。

主要职责：

承载 Web UI。
管理 Python Orchestrator 进程。
管理 Runtime 进程。
提供文件系统权限。
提供本地进程生命周期控制。
打包 Windows、Linux 和 macOS 应用。

第一阶段允许通过浏览器开发 UI，桌面打包在核心闭环稳定后接入。

2.4 工程编排层

选择 Python。

主要职责：

工程文件读写。
Schema 校验。
组件扫描。
依赖解析。
构建任务生成。
CMake 调用。
动态库产物管理。
Runtime 启动。
控制客户端。
代码生成。
自动化测试。
教学课程管理。

Python 不进入实时音频处理回调。

2.5 实时运行时

选择 C++20。

主要职责：

组件加载。
组件实例管理。
Signal Buffer 管理。
执行计划加载。
实时调度。
多任务桥接。
参数提交。
Probe 采集。
运行统计。
音频设备输入输出。

运行时内部允许使用 C++ 类型和模板。对组件和外部集成提供稳定 C ABI。

2.6 组件实现语言

基础组件优先使用 C11。

允许组件使用 C++20，要求：

通过 C ABI 导出。
不将 C++ 对象跨越 ABI 边界。
不在 ABI 中使用 STL。
不通过 ABI 抛出异常。
实时处理函数不进行异常传播。
声明动态内存和实时安全特性。
2.7 PC 音频后端

优先评估 JUCE 和 miniaudio。

JUCE 提供跨平台音频设备、音频 Buffer、文件格式和 DSP 模块，可用于 PC Host、音频设备适配和组件参考实现。生成的嵌入式组件不依赖 JUCE。

选择规则：

需要完整桌面音频生态时使用 JUCE。
需要轻量运行时和简单设备接入时使用 miniaudio。
通过 IAudioBackend 接口隔离具体实现。
2.8 构建系统

选择 CMake 和 Ninja。

需要支持：

单组件动态库构建。
Runtime 构建。
生成工程构建。
测试构建。
多平台预设。
编译缓存。
构建日志结构化解析。
2.9 配置与序列化

使用 YAML 保存用户工程和组件 Manifest。

使用 JSON Schema 校验可编辑配置。

Runtime 使用编译后的中间表示，减少运行前解析工作。中间表示需要包含：

节点实例。
函数入口。
Buffer 地址关系。
执行顺序。
参数初值。
Task 分组。
Probe 配置。
内存布局。
2.10 测试技术

使用：

GoogleTest：C/C++ 组件和 Runtime 单元测试。
pytest：Python 编排、构建和代码生成测试。
Playwright：UI 端到端测试。
Golden File：生成代码结构验证。
WAV 或二进制向量：DSP 一致性验证。
Sanitizer：内存和线程问题检测。
静态分析：Clang-Tidy、Cppcheck。
Schema 测试：Manifest 与工程格式兼容性。

动态 PC 模式
组件构建为动态库。
Runtime 动态加载组件。

支持热重载。
静态 PC 模式

4. 设计中的概念定义和解释

运行配置。

Project 是保存、版本控制、构建和生成代码的基本单位。

Graph 描述组件实例及其连接关系。

Graph 包含：

Node。
Port。
Connection。
Subsystem。
Execution Domain。

Node 包含：

实例 ID。

4.4 Component

Component 由以下内容组成：

Manifest。

公共头文件。
测试。
文档。

可选教学内容。

Manifest 是组件的机器可读契约。

Manifest 描述：

源文件。

Port 是组件接收或输出数据的接口。

端口具有：

方向。
类型。

Control Port 传输参数值和低速连续控制数据。

Control Port 需要声明：

缺省值。

4.9 Event Port

Event Port 传输离散事件。

Event 包含：

时间戳。

来源。
顺序信息。
4.10 Bulk Port

Bulk Port 用于传输大块配置和调音数据。

Bulk Port 支持：

分块写入。

暂存。
提交。
回滚。
4.11 Debug Port

Debug Port 用于输出调试和观察数据。

Debug 数据可以丢弃。实时线程不得等待 Debug 数据被消费。

4.12 Parameter

Parameter 是组件可配置属性。

每个 Parameter 需要声明：

ID。
名称。
类型。
默认值。
范围。
单位。
更新策略。
是否可读回。
是否持久化。
是否触发重新初始化。
UI 控件类型。
4.13 Parameter Update Policy

参数更新策略定义参数何时生效。

支持：

Immediate。
Block Boundary。
Smoothed。
Transactional。
Restart Required。
4.14 Execution Domain

Execution Domain 描述一组具有共同执行条件的节点。

包含：

Sample Rate。
Block Size。
Task ID。
Clock ID。
执行周期。
优先级。
目标核心。

任务周期计算方式：

Task Period = Block Size / Sample Rate


多采样率系统需要分别描述采样率、块长度和块周期。现有 Audio Weaver 的多速率模型同样使用采样率、块长度和 Block Time 描述执行关系。

4.15 Rate Domain

Rate Domain 是具有相同采样率和时钟来源的音频处理区域。

跨 Rate Domain 连接需要显式 Resampler。

4.16 Task Domain

Task Domain 是由同一任务入口调用的节点集合。

跨 Task Domain 连接需要 Task Bridge。

4.17 Clock Domain

Clock Domain 表示数据采样时钟来源。

两个相同标称采样率的设备可能属于不同 Clock Domain。跨异步 Clock Domain 需要缓冲水位监测和异步采样率转换能力。

4.18 Adapter

Adapter 用于转换连接两端的属性。

包括：

Channel Mapper。
Interleave Converter。
Resampler。
Rebuffer。
Task Bridge。
Clock Domain Bridge。

Adapter 作为显式节点保存在 Graph 中。

4.19 Subsystem

Subsystem 是包含内部 Graph 的复合节点。

Subsystem 具有公开端口和公开参数。

支持：

结构型 Subsystem。
封装型 Subsystem。

结构型 Subsystem 在编译和代码生成时展开。封装型 Subsystem 可以形成独立组件或库。

Runtime 持有：

组件实例。
Buffer。
Execution Plan。
参数存储。
Probe。

音频设备。
控制服务。

包含：

内存布局。

4.22 Persistent Memory

Persistent Memory 是组件整个生命周期内持续存在的状态内存。

用于：

延迟线。
包络状态。
重采样相位。
统计状态。
4.23 Scratch Memory

Scratch Memory 是单次执行过程中使用的临时内存。

Runtime 可以根据生命周期在多个组件之间复用 Scratch Memory。

需要声明：

大小。
对齐。

生命周期。
所属内存区域。

Task Bridge 负责：

数据缓存。
Producer 和 Consumer 协调。
欠载与溢出处理。

运行状态统计。
4.26 Probe

Probe 是旁路观察机制。

Probe 可以绑定：

Port。
Parameter。
Component State。
Task。
Buffer。
Runtime Counter。

Probe 使用非阻塞传输，并支持降采样、触发、限流和丢弃。
