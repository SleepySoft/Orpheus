# 驱动入口与 Buffer 分离设计

> 状态：2026-11-06 设计方向定案，详细记录本轮讨论；尚未实施。
> 本文不声明新的 YAML 字段、ABI、UI 或宿主接口已经可用。
> 当前实现仍见[ABI v6 链式调用契约](task-driven-execution-design.md#0-当前实现task-启动入口组件调用下游)。
> 本文取代此前设计中“把 Task 入口当成普通节点/端口”及“由框架匹配调用节拍与数据交付”的方向，
> 但不取代组件主动续调原则，也不因文档定案而改变现有工程行为。

## 1. 核心结论

**执行入口不是一种数据上游，不应该塞进普通组件的数据端口体系。**

图中分别表达：

| 表达 | 语义 |
|---|---|
| 组件节点 | 做什么计算、读取或更新什么状态 |
| 数据端口与连线 | 从哪里读数据、向哪里写数据，绑定哪些 Buffer |
| 指向节点的特殊驱动箭头 | 由什么事件、从哪个节点开始执行一次 |
| 驱动源的分频/选拍分支 | 上游哪些触发拍需要启动对应入口 |

驱动箭头指向**节点本体的执行入口**，不接到节点的 PCM、数组、控制参数等普通端口。
它不携带一种叫“Task”的音频数据，也不要求目标节点有某个虚构的音频输入。
它可以在编辑器中有专用锚点，但不能因此与普通数据 handle 共用语义。
具体箭头外观、锚点位置和交互仍未设计。

用户确认的边界：

> 如果需要分频，只要从 task 源上分一路出来即可，对应的耦合 buffer 输入输出自己配。
> task 分频可以指定几拍驱动一次和几拍抽一拍这样。
> buffer 需要用户自己保证输入输出能对上，系统不管。

这里“系统不管”指**不负责数据吞吐、读写相位和处理节拍的自动匹配**，
不是取消内存访问安全或允许组件静默伪造成功。

## 2. 为什么不再把 Task 入口做成普通节点

此前的纠结来自同一根连接承担了两种不同的职责：

1. 上游给下游提供 PCM。
2. 上游让下游执行。

音频 Source 可以同时完成这两件事，但纯触发事件没有 PCM。
如果强迫它通过普通音频端口连接下游，就会不断产生“裸 Task 如何输出音频”、
“是否要给 Task 拼一个 Buffer”以及“如何构造 Task＋PCM 组合器”等问题。

这不是缺少组合组件，而是把执行关系错误地放进了数据连接。
将启动关系改为指向节点的特殊箭头后，下游的数据来源独立配置：

```text
输入 Buffer ──数据──→ [A] ──数据──→ [B] → [C]
                        ↑
                    特殊驱动箭头
                 音频回调 / 分频 / 外部调用
```

A 被调用，不表示本次 PCM 是由驱动箭头传入的；A 通过自己的数据绑定读取输入。
反之，某个生产者写了数据，也不表示消费者因此自动被调用。

## 3. Source、Task、Pump 各自的位置

### 3.1 Source 是数据或事件的来源，不是必须合并的接口

- 音频设备可以提供输入块，并由回调提供触发。
- WAV 源可以在被驱动时提供下一块数据；文件预读不是处理链的启动事件。
- 一个外部事件或分频分支可以只触发执行，没有音频输出。
- 一个控制入口可以只读取状态、更新参数，不需要人为配一个 PCM Buffer。

普通使用可以把数据提供和默认触发绑定放在一起呈现，但两者的配置和含义必须可区分。
不能仅因某个节点叫 Source，就隐含它创建线程、定时器或驱动全部相连的数据消费者。

### 3.2 Task 不再是图中必经的普通组件

目标不是要求用户画出：

```text
Task 节点 → Task＋PCM 组合器 → 算法
```

“Task 源”在讨论中表示驱动事件的来源。即使编辑器显示为一个可分支的驱动源标记，
它也属于执行表达，不是普通 PCM 组件。

是否在宿主或内部保留名为 Task 的执行对象、如何绑定线程或中断，留待实施时决定。
移除图中的 Task 节点，不等于线程、优先级、串行化和重入问题消失。
不能仅通过本设计推导“每个入口必有独立线程”或“全部入口必在同一线程执行”。

### 3.3 Pump 是一次推进动作

Pump 表示对指定入口发起一次执行，不是第三种数据，也不必额外做成普通节点。

- 对音频读入口：按该入口的 Buffer 读出配置取得数据，然后启动下游。
- 对 WAV 等生产入口：执行该组件约定的数据生产，再启动下游。
- 对无音频入口：执行控制或状态处理，再按组件逻辑续调。

“一次 Pump”不保证全图所有节点各执行一次，也不意味着遍历拓扑列表。
如果组件没有续调，执行在该处结束；如果组件重复续调，下游可以执行多次。

## 4. 执行仍采用组件链式调用

特殊驱动箭头只决定入口，不维护一份由宿主逐项调用的算法列表：

```text
事件到达 → 调用 A
                A 自己续调 B
                          B 自己续调 C
```

- 驱动源只启动该分支指定的直接入口。
- 后续执行由组件主动续调，动态 Runtime 和生成代码采用同一语义。
- 不恢复逐节点调度器，不因数据依赖补调生产者。
- 不增加会合等待、每拍去重或“全部输入生产者完成后自动调用”的规则。
- 多条调用路线到达同一组件时，执行次数由真实调用决定，不按图节点身份合并。
- 数据连接不能隐式启动另一个驱动入口或跨越执行边界。

组件间续调关系需要明确保存，不能拿画布位置或普通数据连线猜测。
现有调用连接与新的节点级入口标记如何映射、如何保存复合组件边界，
属于后续格式和编译实现工作，本文不把新的字段名提前定成接口。

## 5. 分频与选拍：只操作触发事件

### 5.1 从驱动源分支

```text
驱动源 ─────────────────▶ A 的驱动入口
      └─ 分频 / 选拍 ────▶ B 的驱动入口

数据关系另外配置：
A → Buffer 写端 …… Buffer 读端 → B
```

慢速链路不需要在 PCM 线上插入一个隐含 Task 切换。
分频从驱动源分支产生，选中的事件启动对应节点入口。
分频到底画成箭头属性、分支标记还是专用执行控件，尚未确定；
无论采用哪种形式，都不能伪装成需要音频输入输出的算法模块。

### 5.2 拍的含义

拍是**上游驱动事件的计数**，不是 PCM 样本计数，也不是自动产生的墙钟定时。

- “几拍驱动一次”：按触发事件的周期推进目标入口。
- “几拍抽一拍”：按明确的选拍规则传递部分触发事件。
- 起始相位、第一拍编号、启停/复位后的计数行为，必须在实施时明确。
- 如果两个表述最终对应相同的周期选拍行为，应统一语义，不制造两种只有名称不同的机制。
- 这些配置不表示抽取音频采样点，不承担滤波、音频降采样或重采样。

例如“每 4 拍一次”只说明 B 的触发频率，不能据此推导 B 应读 4 倍帧数、
读取最新一块还是历史窗口。本文也不预定第一次触发在第 1 拍还是第 4 拍。

### 5.3 同源分支不隐含数据就绪

两个入口来自同一驱动源，不表示它们已经建立“先写完再读”的完成依赖。
如果用户需要先写 Buffer 再消费，必须通过明确的调用先后和读写配置表达。
若映射到不同线程，还必须使用符合交接契约的存储与发布方式。
仅有相同周期、相同相位或画在同一分支附近，都不能代替这些事实。

## 6. Buffer：显式数据绑定与用户负责的匹配

### 6.1 组件通过端口取得数据

普通算法组件的输入输出通过数据端口绑定 Buffer 引用。
处理函数可以通过上下文访问已绑定的输入输出，不需要把地址塞进可调参数表：

```text
process(ctx)
    读取已绑定的输入块
    写入已绑定的输出块
    按组件实现续调
```

这是语义示意，不是新增 ABI。
“不通过参数传递 Buffer”不表示数据依赖消失，更不表示所有组件偷偷读取全局变量。
应区分可调参数、处理函数实参、上下文引用和显式存储绑定。

普通 EQ 等组件通常只需认识当前音频块，不必知道底层是 DMA 双缓冲、
环形队列还是文件预读缓存。存储读写端负责暴露相应的数据视图。

### 6.2 显式读写配置

根据所用 Buffer 组件，用户可能需要配置：

- 数据类型、通道选择、通道顺序和布局；
- 每次写入/读出的帧数、窗口长度和步长；
- 容量、各读出口的游标、覆盖和保持策略；
- 初始化、历史预填充、复位行为；
- 欠载/溢出时该组件约定的处理方式；
- 多个执行入口之间的发布、可见性与有效期。

这是一份配置职责清单，不要求所有 Buffer 组件都暴露同一组字段，
也不预定每个读操作一定消费数据；窗口读取、查看和队列消费应由具体契约区分。

### 6.3 不做自动匹配

**用户负责 Buffer 输入输出与驱动节拍能否对上。系统不负责：**

- 自动证明生产量与消费量匹配；
- 强制生产者、消费者调用周期和相位相等；
- 因配置不匹配而自动重排或延后调用；
- 自动补齐、重复旧数据、丢帧或重采样以“修复”吞吐；
- 自动插入桥、队列或数据适配组件；
- 因为攒满而自动驱动消费者，或因为水位不足而擅自跳过、补跑执行；
- 把没有新数据的音频调用悄悄转换成一次无音频调用。

有意的补零、覆盖、丢弃或保持可以是某个 Buffer 的**显式策略**，
不能成为框架在用户不知情时执行的成功形回退。

### 6.4 仍须遵守访问安全

放开匹配责任，不表示允许越界、悬空指针、非法形状或并发破坏存储。
框架和组件仍须遵守各自的内存与访问契约；失败按标准错误/探针路径报告，
不能静默吞掉。基础合法性检查与跨链吞吐/时序匹配是两类不同职责。

Buffer 就绪、水位和溢出计数用于说明数据状态，不自动改变驱动规则。
普通端口工作内存的分配、复用和原地处理，也不能改变用户声明的存储共享语义。
具体的原地能力声明与内存规划接口不在本轮定案范围。

## 7. 四个表达示例

### 7.1 简单音频流

```text
音频回调 ──写入──→ 输入 Buffer
        └─驱动───▶ 读取入口 → EQ → 输出处理
                         ↑
                  绑定输入 Buffer
```

普通界面可以将输入 Buffer、读入口和默认回调绑定组合显示为音频 Source，
高级视图可以展开。无需用户额外创建一个 Task＋PCM 组合器。

### 7.2 分频窗口分析

```text
音频驱动源 ─────────▶ 音频链 → 历史 Buffer 写端
          └─选拍─────▶ 窗口读取入口 → 分析链
                              ↑
                       绑定历史 Buffer 读端
```

窗口长度、步长、首帧历史和触发拍由用户匹配。
分频器不替用户计算窗口，也不因历史攒满而改变第一次触发时刻。

### 7.3 无音频控制链

```text
外部事件 / 分频分支 ──▶ 状态更新 → 参数计算 → 参数写入
```

驱动箭头直接指向状态更新节点，不需要虚构 PCM 端口或空音频 Buffer。

### 7.4 独立驱动的两条链

```text
驱动源 A ──▶ 生产链 → 显式 Buffer 写端
驱动源 B ──▶ 显式 Buffer 读入口 → 消费链
```

两条链可以具有不同节拍。Buffer 的交接方式及欠载/溢出策略由用户选择；
框架不因看到两个驱动源，就自动建立同步屏障或补上采样率适配。

## 8. 与当前实现的区别及后续边界

当前 ABI v6 已经支持组件主动续调，但仍存在 `clock_source` 对应逻辑 Task、
`task_source` 节点、`source:out → target:in` 驱动接口以及编译期交付节拍检查等契约。
这些事实不因本文记录而立即改变。

后续实施应分别处理：

1. 节点级特殊驱动箭头、驱动源分支和可展开的默认绑定。
2. 入口/分频声明的持久化、复合组件映射和可观测触发计数。
3. 不依赖普通 PCM 端口的入口调用，以及纯控制入口。
4. 数据端口、显式存储绑定与组件续调关系的独立保存。
5. 取消由框架强制进行的数据交付/消费节拍匹配，保留基础合法性与访问安全检查。
6. Runtime、生成代码、宿主接入和相关验证采用同一套新语义。

本轮只记录设计，不修改编译器、Runtime、ABI、UI、组件或研究工程。
YAML/API 命名、分频精确定义、线程绑定、复位和时间戳规则需在实施前明确，
不能用本文中的概念示意冒充已实现接口。

## 9. 与 AWE 的关系

AWE 的有序模块列表、预绑定 Wire 和集中 Pump 派发帮助澄清了“数据在哪里”与
“何时执行”是不同问题；不能据此宣称 Orpheus 将照搬其列表执行。

本轮采用的是**数据绑定与驱动入口分离的表达**，保留 Orpheus 的组件链式续调，
并明确由用户负责缓冲读写和驱动节拍的设计匹配。
