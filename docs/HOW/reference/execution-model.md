# 执行、触发与访问模型

> 状态：术语定案（v1）。本文是 UI、API、文档和错误信息描述“如何运行”的统一依据。

## 1. 三个顶层维度

“实时运行”“离线运行”“动态运行”“串口运行”等旧说法混合了不同问题：图由谁执行、由谁推进、推进多快、UI 连接到哪里。它们不能互相替代。

Orpheus 统一使用三个正交的顶层维度；pacing 降为主动推进的子配置：

| 顶层维度 | 回答的问题 | 取值 | 是否由用户直接选择 |
|---|---|---|---|
| **执行实现** | 哪套代码执行图？ | 动态 Runtime / 生成代码 | 是 |
| **执行触发** | 谁决定何时推进下一个音频块？ | 外部节拍触发 / 主动推进 | 否，由有效图与宿主自动推导 |
| **访问端点** | UI/SDK 连接到哪个正在运行的实例？ | 本机 / 串口 / 未来 TCP、SHM 等 | 是 |

主动推进再包含一项运行策略：

```text
执行触发
├── 外部节拍触发：推进时刻由 callback / DMA / Timer 决定
└── 主动推进：执行器循环调用 process
    └── pacing：全速 / 按现实时间
```

三个顶层维度组合出具体运行形态，但不增加新的图语义。WAV、声卡、信号发生器和输出文件仍由图中的组件决定。

## 2. 执行实现

### 2.1 动态 Runtime

UI 的“▶ 运行”使用此实现：

```text
project.yaml -> plan.json -> C++ Runtime -> 动态组件库
```

特点：

- 修改图后不重新编译 C；
- 适合 PC 设计、调试和快速迭代；
- 根据图的有效设备组件，自动选择 `orpheus_rt_host` 或 `orpheus_runtime`；
- 与生成代码共享组件源码、ABI、plan 语义和一致性测试。

### 2.2 生成代码

UI 的“⚙ 编译后运行”或 CLI `generate` 使用此实现：

```text
project.yaml -> plan -> 独立 C 工程 -> orpheus_graph 静态库
```

特点：

- 组件静态链接，无 DLL、Python 依赖；
- `orpheus_graph.c/.h` 是产品图本体，用户可从自己的 main、音频回调或中断调用；
- 生成的最小 `main.c`、Windows 声卡宿主和 PC CLI 都只是宿主示例；
- 可部署到 PC、DSP、MCU 或 SoC。

“生成代码”本身不是运行；只有构建并调用 `orpheus_graph` 后才发生执行。

## 3. 执行触发

### 3.1 外部节拍触发

有效图含 `device_in` 或 `device_out` 时，宿主由声卡回调触发图处理：

```text
声卡硬件回调 -> process(block) -> 声卡/文件
```

性质：

- 处理 5 秒音频约占用 5 秒现实时间；
- 通常持续运行，直到用户停止；
- 每个块必须在 deadline 内完成，否则产生欠载、溢出或爆音；
- 设备回调帧数与图 tick 不同时，宿主必须分块调用图入口。

外部节拍触发并不等于动态 Runtime。生成的 Windows 声卡宿主、MCU DMA ISR 或硬件 Timer 同样可以触发静态 `orpheus_graph`。

### 3.2 主动推进

有效图不含设备组件时，普通循环主动推进图：

```text
for each block:
    process(tick)
```

典型图：

- `wav_in -> DSP -> wav_out`；
- `signal_gen -> DSP -> sweep_record`；
- 自动化测试和 Golden Vector。

这类运行过去称为“离线运行”。统一术语改为 **无设备批处理** 或 **主动推进运行**。“离线”不表示没有网络，只表示不受外部设备节拍触发。

主动推进必须有终止条件，例如 WAV 总帧数、`duration_s` 或显式块数。它的 `pacing` 子配置决定执行器循环是否等待墙钟。

### 3.3 主动推进的 pacing

`pacing` 不是顶层运行维度，只是主动推进器的策略。外部节拍触发没有该配置，因为 callback/ISR/Timer 已经决定推进时刻。

#### 全速

宿主不等待墙钟，CPU 能跑多快就跑多快。

例如 48 kHz、5 秒的信号始终计算 240,000 帧，但可能只花 0.1 秒现实时间。适合：

- WAV 转换与批处理；
- 单元测试、性能测试；
- 扫频和批处理分析；
- 快速生成输出文件。

#### 按现实时间

宿主在块之间等待，使图时间接近墙钟时间。当前对应 `orpheus_runtime --pace` 和 UI 的“真实时长”。

同一段 5 秒信号仍计算 240,000 帧，但约用 5 秒完成。用途是：

- 在 UI 中连续观察 Probe、进度和曲线；
- 模拟实时交互节奏；
- 演示或听感检查。

它不是硬实时保证，也没有自动变成声卡运行。调度晚了可以继续，外部节拍触发则必须满足硬件 deadline。

#### 适用规则

| 执行触发 | 全速 | 按现实时间 |
|---|---|---|
| 主动推进 | 可选，默认 | 可选 |
| 外部节拍触发 | 不适用 | 天然如此，不显示该选项 |

建议 UI 将“真实时长”重命名为“批处理节奏：全速 / 按现实时间”，并只在无设备图中显示。

### 3.4 为什么不放进 source 参数

`wav_in`、`mp3_in`、`signal_gen`、`sweep_gen` 是数据源和图内时间根；真正执行等待的是外部执行器循环。两者不是同一个职责。

不把 `pacing` 放进普通 source 参数，原因是：

- 同一工程需要不改图即可在全速测试和按现实时间观察之间切换；
- 一个图可包含多个兼容 source，无法定义哪个 source 的 pacing 获胜；
- source 可能位于可复用子组件内，宿主策略不应被子组件固化；
- 生成到 MCU/DSP 后由用户硬件宿主驱动，PC 的墙钟等待参数没有意义；
- `pacing` 不改变采样帧、DSP 结果和图语义，只改变本次运行的墙钟耗时。

因此当前 `pacing` 是运行会话配置（UI 状态 / API `pace`）。若未来需要保存默认值，应使用工程级主动推进配置，例如 `active_runner.pacing: fast|wall_clock`，而不是组件参数。

组件 manifest 的 `clock_source` / `clock_domain` 继续描述图内时间根与时钟域兼容性；它们不承担执行触发或 pacing 策略。图时间线的完整演进见 `design_timeline.md`。

## 4. 访问端点

访问端点决定 UI/SDK 连接谁，不决定图在哪里执行：

- **本机**：连接本机动态 Runtime 或本机生成宿主；
- **串口 COMx**：连接已在远程设备运行的生成图；
- **未来 TCP/SHM**：连接网络设备或本机共享内存实例。

串口连接时 PC 不启动另一份音频图，只控制和观察远程实例。工程顶层 `bridges` 描述目标侧 Bridge；工具栏端点选择描述本次主机连接，两者不能混为同一配置。

详见 `design_access_bridge.md`。

## 5. UI 操作与三轴映射

| UI 操作 | 执行实现 | 是否执行 | 说明 |
|---|---|---|---|
| **编译** | 无 | 否 | YAML -> plan，校验拓扑、签名、时钟、平台和 Bridge |
| **▶ 运行** | 动态 Runtime | 是 | 执行触发由有效图与宿主推导；主动推进时可选 pacing |
| **⚙ 编译后运行** | 生成代码 | 是 | 生成 C、构建，再启动对应宿主 |
| **⤓ 生成代码** | 生成代码 | 否 | 只产生独立工程，交给用户集成或部署 |
| **连接串口端点** | 远程已有实例 | 不启动图 | 建立 Access Bridge 会话 |

## 6. 当前组合矩阵

| 执行实现 | 执行触发 | 主动推进 pacing | 当前宿主 |
|---|---|---|---|
| 动态 Runtime | 外部节拍触发 | 不适用 | `orpheus_rt_host` |
| 动态 Runtime | 主动推进 | 全速 | `orpheus_runtime` |
| 动态 Runtime | 主动推进 | 按现实时间 | `orpheus_runtime --pace` |
| 生成代码 | 外部节拍触发 | 不适用 | `host_win` 或用户硬件宿主 |
| 生成代码 | 主动推进 | 全速 | 最小 `main.c` / 用户 main |
| 生成代码 | 主动推进 | 按现实时间 | 用户宿主负责等待；PC CLI 可扩展 |

## 7. 命名规则

新代码和文档遵循：

- 用“动态 Runtime / 生成代码”描述执行实现；
- 用“外部节拍触发 / 主动推进”描述执行触发；
- 仅在主动推进下用“全速 / 按现实时间”描述 pacing；
- 用 `clock_source / clock_domain / timeline` 描述图时间线，不将其称为运行模式；
- 用“本机 / 串口 / TCP / SHM”描述访问端点；
- “无设备批处理（旧称离线运行）”可在迁移期并列出现；
- 不使用“串口运行”描述远程连接；
- 不把“按现实时间”简称为“实时运行”。

## 8. 示例

### 8.1 快速处理 WAV

```text
执行实现：动态 Runtime
执行触发：主动推进（pacing=全速）
访问端点：本机
```

### 8.2 观察 5 秒扫频过程

```text
执行实现：动态 Runtime
执行触发：主动推进（pacing=按现实时间）
访问端点：本机
```

### 8.3 PC 实时耳机 EQ

```text
执行实现：动态 Runtime
执行触发：外部节拍触发（声卡 callback）
访问端点：本机
```

### 8.4 MCU 上运行并由 UI 串口调音

```text
执行实现：生成代码
执行触发：外部节拍触发（DMA/ISR）
访问端点：串口 COM5
```

其中 `COM5` 是主机端点；工程 Bridge 的 `resource: uart2` 是设备侧逻辑资源。
