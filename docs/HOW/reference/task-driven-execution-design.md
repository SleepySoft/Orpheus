# Source驱动的组件链式调用

> 状态：2026-11-04 改为组件主动续接（ABI v6）。第 0 节为当前契约；
> 后文仍包含后续设计，不表示任意循环、重复调用、共享存储或宿主线程映射已经实现。
> 本次不修改具体模型/研究工程。

## 0. 当前实现：Task 启动入口，组件调用下游

Runtime 和生成 C 均不再扫描 `execution_order` 逐节点执行。Task 只启动
`entry_nodes`；组件的 `process` 通过 ABI v6 续接接口同步调用其直接下游。
`execution_order` 只保留编译分析、内存布局及工具展示用途，不是运行时调用表。

```c
static int process(void* state, const OrpheusProcessContext* ctx) {
    /* 完成本组件计算和输出后，同步调用直接下游。 */
    return orpheus_process_next(ctx);
}
```

- 不调用续接接口便停止本条链；返回成功不会由 Runtime 自动补调下游。
- `orpheus_process_next(ctx)` 按声明顺序调用全部直接下游；
  `orpheus_process_branch(ctx, index)` 只调用指定的零基分支。
- 续接可重复调用，适用于组件内循环、逐小块交付；调用栈正常嵌套，
  下游返回后继续上游尚未完成的代码。续接上下文仅在本次 `process` 内有效，
  不可保存到异步线程或下一次调用中使用。
- 不设置会合屏障、不等待其它分支、不做每拍去重。`A → B → D` 与
  `A → C → D` 会自然执行 `A, B, D, C, D`，D 执行两次。
- `every/phase` 在每条调用边局部计数，按上游实际续接次数分频；
  上游停止传播时不会由静态周期表补跑下游。重复续接也计入分频。
- 组件必须返回续接错误，后续兄弟分支不再调用。已执行组件不回滚。
- `call_graph` 保存直接调用连接及 `every/phase`；动态与生成实现共用
  `orpheus_chain.h` 的连接调用逻辑。只有 Task 入口按宿主节拍触发，
  中间组件不再受逐节点 period 门控；绝对帧位置按实际调用次数推进。
- 数据流图的音频/数据边直接形成调用连接；显式 `task_sequence` 图只读取
  `drive_connections`，数据线和参数线不会偷偷增加调用。
- 组块、重采样和拆块只负责数据生产/消费；缓冲就绪或水位变化不是执行触发。
  消费链由关联 Task（例如 Source 派生的分频调用）按声明周期/相位触发，
  不由生产组件在“攒满”时自动启动。数据线不代替跨频率调用连接。
- 跨 Task 仍用显式数据桥，不沿数据连接递归调用另一个 Task。桥缓冲在组件
  续接之前发布，确保同步下游可见。框架不为会合节点增加同步规则。
- 不保留旧调度器或旧 ABI DLL 兼容路径。所有组件须以 ABI v6 重建；
  自定义组件须在适当位置显式调用续接接口。无续接的组件就是链路终点。

例如组块写入和消费使用两条独立驱动分支：

```yaml
drive_connections:
  - {from: "source:out", to: "batch:in"}
  - {from: "source:out", to: "consumer:in", every: 2, phase: 1}
graph:
  connections:
    - {from: "source:out", to: "batch:in"}
    - {from: "batch:out", to: "consumer:in"}
```

第一拍只写入，第二拍先写入再进入消费链。`batch` 不驱动 `consumer`；
消费相位由分频声明决定，不跟随缓冲攒满时刻漂移。水位只用于数据有效性和
既定欠载/溢出处理，不会由框架改成等待、跳过或补跑 Task。

### 工程声明与参数交付

新工程契约示例：

```yaml
flow_mode: task_sequence
drive_connections:
  - {from: "source:out", to: "a:in"}
  - {from: "a:out", to: "b:in", every: 2, phase: 1}
```

这里的 `in/out` 是独立的框架驱动接口，不是同名数据端口，不分配 Buffer，
也不占组件 ABI 的 `inputs/outputs` 槽。数据仍用 `graph.connections`，
参数仍用 `control_connections`，三种连线分别保存。

- 每个 `clock_source: true` 的 Source 对应一个逻辑 Task。没有显式 Task 名称时，
  自动使用 `task_<Source实例ID>`；已有非 `default` Task 配置可继续绑定。
- Task 内只根据直接驱动连接进行嵌套调用，同一实例可被多次调用。
  数据依赖和同 Task 参数读取须满足显式嵌套调用的先后顺序，
  可以使用按声明顺序执行的兄弟分支，
  不再用数据线或画布/节点存储顺序偷偷补调用关系。
- `every` 是相对上游调用的正整数分频；`phase` 是 `[0, every)` 内的零基相位，
  缺省 `every-1`。嵌套分频在各连接独立执行，不要求会合分支的调用节拍相同。
- 时间戳按声明的输入量锚定在当前 Source 入口块的结束边界：
  32帧源中，每两次执行一次的32帧稀疏调用首次起点为32，
  两块聚合的64帧调用首次起点为0，不混用同一“首次一律为0”的公式。
  `frame_origin/frame_step` 进入同一 Plan；负起点或非整数样本起点明确拒绝，
  不靠读取实现猜测预填充。具名 `_at` 入口同样按调用的数据量换算。
- 输出端口缺省跟随本节点调用；异频输出用
  `cadence: {period: <整数或参数表达式>, phase: <整数或参数表达式>}` 显式声明，
  相位缺省 `period-1`。已有 `scheduling.divisor` 仍是显式输出契约，可作为默认值。
  普通同步数据输入的交付周期/相位须匹配目标调用；
  同 Task 非音频 `timing: latest` 可显式读取旧值。框架不阅读 C 代码猜测频率。
- 新模式的同 Task 参数链在**目标本次调用之前**读取该目标的全部源快照，
  再应用标量 setter / typed BULK，并立即使本次 BULK active 数据生效；
  不再附加旧块末控制快照。组件自身的平滑策略仍由组件处理。
- 外部 BULK 待写按目标 Task 的入口提交；Task B 不代为提交 Task A。
  这不意味着已引入任意跨线程标量事务或允许并发直接访问同一实例。
- 复合定义在 `graph.drive_connections` 声明内部调用，边界展开到内部入口/出口；
  每个复合实例保留独立实例身份。未声明的内部数据依赖仍会明确拒绝，而非猜测顺序。
- 新增无音频的“任务驱动源” `orpheus.builtin.task_source`；
  `frequency_hz` 缺省 100，仅用于软件定时 Task，必须精确整除 Task 时间基准采样率。
  音频 Source 仍由采样率/块长推导节拍，不必另填 Hz。
  Plan 的 Task 包含 `source`、`frequency_hz` 和局部 `periods/phases`，
  嵌入式可据此接入对应的生成 Task 入口。

当前边界：

- 多 Source 必须使用独立 Task 入口，不提供“同时推进所有独立时钟”的全局入口；
  既有异步音频桥仍可交付跨 Task 数据，参数不得隐式跨 Task。
- PC 继续复用已有宿主推进/回调和 pacing，尚不自动为任意多个定时 Source 创建独立线程。
  `frequency_hz` 是时间契约，不表示全速离线推进已经变成真实时间等待。
- 条件和重复调用由组件的 C 实现决定；驱动图仍要求无环。
  编辑器中的独立条件/循环节点、共享数据节点和跨 Task 参数事务仍属于后续工作。
- ABI 已升级至 v6；未修改具体算法研究工程来适配框架。

可直接导入[无音频 Task 示例](../../../examples/task_sequence_demo.yaml)，
100Hz入口驱动两个数组节点，消费者50Hz，参数值在该消费者实际调用之前交付。

## 1. 早期迁移讨论（历史记录，执行方式以第 0 节为准）

1. Task是代码的驱动者，Task内部按明确流程顺序调用组件。
2. 一个Source天然对应一个逻辑Task；Task不等于线程，不为每个Source强制创建线程。
3. 后续讨论改为优先提供显式“仅驱动”接口：Source的数据输出与执行驱动分开，
   Task/组件可通过同类执行接口关联，不借参数数值传递表达一次调用。
4. 只需要Task驱动的组件使用驱动接口，不必虚接音频；
   普通音频连接继续表达音频数据关系，数组尺寸不因此变成音频时间长度。
   此项取代前一轮“音频线连上后忽略样本”的优先方案；旧工程兼容规则另行处理。
5. 改动主体是框架：编译/Plan、Runtime调用、代码生成和参数交付。
   不修改公司算法、蒸馏叶子、具体研究工程或其布局来适配框架。
6. 工程描述/Schema、编辑器和兼容加载属于框架契约；若需要新增表达能力，
   应由框架提供并兼容旧工程，不要求用户逐个手改模型。

## 2. 为什么不是简单更换调度循环

当前已经具有：

- 工程Task及独立Task入口；
- Plan中的每Task执行顺序和局部周期；
- Runtime按顺序调用节点，生成代码按同一Plan展开；
- 同Task参数控制连接的块末两相快照；
- 跨Task音频的显式桥接。

参见[现有多Task实现](multitask-runtime.md)和[现有参数交付](control-links.md)。

因此，“把节点改成顺序调用”本身不是全新能力。需要改变/补齐的是：

- Source到Task入口的驱动关系明确化；
- 独立驱动接口可以组织调用，而不要求消费音频样本；
- Task调用流程成为可检查的执行事实，不再把任意原程序强行解释为一次拓扑遍历；
- 参数调用可以在Task内的指定位置执行；
- Runtime和生成路径对调用次数、顺序及状态使用相同定义。

统一静态调用顺序并不等于运行期全局协调。
例如`A(); B(); C(); D();`既是普通顺序程序，也是一份静态执行安排。
本次不是为了消灭所有“调度”概念，而是避免丢失明确调用流程。

## 3. Source与显式驱动接口

### 3.1 驱动入口

```text
音频Source的一次有效推进
    → 对应Task入口
    → 顺序调用本次应执行的组件
    → 完成本次输出/显式交付
```

由宿主、设备回调或主动推进循环进入Task；Source的数据产生与Task执行不能
互相递归触发，也不能在同一次入口中把Source处理两次。
Source的“源组件”含义与manifest的`package_type: source`（源码包）无关，
后者不能作为创建Task的判断依据。

Task仍可由同一宿主串行调用，之后再按平台需要映射到线程、中断或外部任务。
外部节拍、主动推进及pacing继续沿用原术语，不新增第三种执行实现。

### 3.2 数据接口与调用接口

```text
Source
  ├─ 数据输出：音频/数组
  └─ 驱动输出：发起一次执行

Task/组件
  └─ 驱动入口：执行一次流程/调用
```

驱动连接的框架要求：

- 参与Task归属与本次调用关系，不因为没有数据输出消费者就被裁剪。
- 不要求组件对音频做占位乘法、求和或复制。
- 不改变其已有BULK/参数端口的类型、形状和槽顺序；
  框架管理的驱动关联不能偷偷插入ABI输入数组，令旧组件的`inputs[0]`变成音频。
- 不逐个修改工程定制算法来补虚假的音频数据口；
  现有音频连接如何兼容推导调用关系，由框架适配。
- 驱动携带/关联必要的调用时间上下文，不把频谱、参数表或历史数组元素数当音频时间。
- 不擅自跨越组件的enable、reset或其它条件：本次是否执行仍属于调用流程。
- 同Task内的同步调用和跨Task的事件交付须区分，不能因接口外观相同就假设同一调用栈。

具体端口元数据/编辑器表示在实现阶段确定；驱动接口不复用旧参数控制边的块末数值快照语义。

### 3.3 Task频率、继承和“2抽1”（讨论中）

执行流程改为Task顺序调用，不意味着取消时间/速率分析。
应区分Task入口触发周期、采样数据的采样率、调用步骤的次数/相位，以及执行耗时和deadline。

候选原则：

- 每个Task有明确驱动来源，但不强制每个Task独立填写一个Hz。
- 音频驱动的名义周期由采样率与每次推进帧数推导；软件定时驱动需要周期配置。
- 外部中断/事件按实际到达触发，名义周期用于检查，不能另造软件时钟追赶硬件。
- PC线程是执行载体，可按周期推进或等待事件；不保证一个线程定时器就是实际音频时钟。
- 嵌入式生成Task入口及调用要求：如“每收到128帧48kHz音频调用一次，名义375Hz”，
  或“每20ms调用一次”，或“事件到达调用，无固定频率”。

“每两个上游节拍执行一次”可传播出二倍周期，但还需要相位。
例如从上游0、2、4次执行，与从1、3、5次执行的频率相同，启动和交付时刻不同。
若以共同根节拍记录父周期P、相位p，子调用每k次取第r次，
其候选时间关系为周期kP、相位p+rP（约定0<=r<k，并明确冷启动/计数器初值）。
这不是要求由中央调度器逐节点轮询，而是为显式调用流程提供静态检查信息。

需区分三种不同含义：

1. 每两个Task入口调用一次组件：有确定入口节拍时可推导调用周期及相位。
2. 一次Task内循环8次、每两次调用一次：每个入口有4次调用，
   但不能假定它们在现实时间中等间隔，或当成4倍频率的独立Task。
3. 音频采样点2抽1：改变采样数据速率，与仅减少函数调用次数不是同一操作；
   是否累积两块再整块处理、丢弃数据或取最近值，必须由数据契约说明。

SPORT示例（仅为时间分析示意，不宣称对应公司工程的具体配置）：

```text
共同采样率：48kHz
SPORT每32帧交付/取数：1500次/秒
步骤B每64帧处理一次：750次/秒
步骤C每96帧处理一次：500次/秒
重复对齐窗口：LCM(32,64,96)=192帧
```

LCM在共同采样时间轴的帧量子上计算，不直接对Hz求LCM。
192帧是上述节拍重复对齐的窗口，不自动意味着每个buffer必须分配192帧。
容量、启动预填充与读写水位还取决于调用相位、先生产还是先消费、允许延迟和最坏完成时间。
异步或有漂移的不同硬件时钟不能仅靠名义频率的LCM证明长期同步，
需要明确的数据交付/异步桥策略。

以上是待讨论的分析约束，不是本轮已实现的调度或参数字段。

### 3.4 端口级输入与输出频率

用户已确认：默认输入与输出同节拍；若不相同，组件必须显式声明。
框架不通过分析组件代码或观察运行结果来猜测频率关系。
默认约定不等于给整个模块永久绑定一个频率：显式声明不同时，应分别检查相关端口。

框架只依据默认契约和显式声明传播、推导及校验：

- 模块的调用触发条件/频率；
- 每个输入的数据交付周期、相位和每次有效数据量；
- 每个输出产生新数据的周期、相位和每次有效数据量；
- 采样数据的采样率与时间区间；不能把数组更新频率当采样率；
- 未产生新输出时的行为：保持最近值还是本次无有效交付；
  下游是每次调用读取最近值，还是仅在新输出交付时执行，须明确。

例如48kHz数据，每次输入64帧并调用模块，累积两次后交付128帧：

```text
模块调用/输入交付：750次/秒，每次64帧
输出交付：375次/秒，每次128帧，首次在第二次输入后
输入与输出采样率：均为48kHz
```

输出交付频率减半不表示采样率减半，也不表示中间一次调用交付了零数据块。
实现应按声明更新有效交付信息，不能仅凭buffer仍有旧值就认为产生了新结果。
不同节拍必须显式声明倍率/周期及必要相位，不要求所有端口重复手填Hz；
由声明推导实际频率，不等于从实现代码猜测。条件性输出也必须声明条件性，
不能因代码内部条件跳过就让框架自行推测或伪造稳定频率。

具体Schema及运行期有效性表示尚未实现；该要求需要贯通编译检查、Runtime、
代码生成与驱动传播，而不只是UI上的频率标注。

## 4. Task内部调用语义

### 4.1 调用实例，不是复制实例

Task程序应能区分实例与调用位置：

```text
调用实例B
更新一项共享数据或参数
再次调用同一个实例B
```

第二次调用延续同一份实例状态，不能用复制一个节点冒充。
多次调用也不能仅靠在旧`execution_order`重复ID实现：
每个调用点的数据绑定、处理量、时间元数据与观测位置都必须明确。

建议在内部Plan中区分：

- 组件实例及其状态/资源；
- Task调用步骤及其顺序；
- 每一步的数据/参数访问与调用上下文。

这是一项内部表示建议，不要求立即在工程YAML中增加同名字段。

### 4.2 顺序、分支和循环

- 顺序明确时，直接执行顺序调用。
- 条件不满足时跳过调用，实例状态不被暗中推进。
- 循环重复的是指定调用步骤，不自动推进整个Task时间或复位状态。
- 每次Task入口只推进一次Task时间；组件调用时间如何对应样本区间须显式定义，
  不能无条件套用旧“每节点每周期一次”的时间公式。
- 实时循环需有可验证上界；不能把不受限的动态循环引入实时路径。

第一阶段不必同时开放所有控制结构，但不能宣称只增加一个顺序列表就已支持任意程序。

### 4.3 分支与合流

同Task内已明确执行`A → B → C → D`时，D在B/C之后运行，不另加等待节点。
只有按到达触发或跨Task交付的位置才需要显式合流/就绪规则。
同一串行Task中的首次到达不能阻塞等待尚未执行的分支。

不同Source的流程相遇时，不得悄悄把两个入口合成一个Task，
也不得由两个Task无保护地调用同一个有状态实例。
应显式确定接收Task、对应数据批次/时间区间及交付/触发方式；
跨Task数据面优先复用现有桥能力，不把音频驱动线直接当作共享可写内存。

## 5. 参数交换：区分调用与外部投递

以下是新Task调用模式的建议语义，不能静默套用到旧工程。

| 场景 | 建议生效规则 |
|---|---|
| 同Task的显式set/get或参数赋值步骤 | 在该步骤执行；后续调用看到新值，不默认延迟到下一块 |
| 外部UI/Bridge参数写入 | 排队到明确的Task入口安全点，由所属Task应用 |
| 跨Task参数/数组交付 | 显式消息、快照或桥；不得假定同一调用栈或共享地址立即可见 |
| restart_required或影响签名的配置 | 继续遵循重建/重启规则，不因顺序调用变成实时可改 |
| 旧control_connections | 保持旧块末快照语义，直到用户明确迁移 |

例如：

```text
set B.gain = 2
call B
```

必须在本次B调用前完成实际应用，包括组件参数回调、校验和必要的更新动作，
而非仅写入一个仍待下一块提交的控制bank。

标量与BULK都需要相同的调用位置语义；沿用现有类型、shape、策略和错误检查。
数组型参数不因数据大就必须改成引用；共享引用也不能冒充参数setter，
绕过组件的状态一致性或系数更新动作。

一组需要原子生效的参数应以明确事务/调用步骤描述；不得自动把若干独立写入视为原子。
调用失败立即返回错误，不继续执行依赖该写入的后续步骤；
已发生的计算或状态修改不承诺回滚，错误位置必须可定位。

## 6. 共享数据与控制连接的边界

通用存储模块/数据buffer节点仍是候选能力：

- 存储可属于工程/子系统，不必属于某个计算节点。
- 引用连接或命名引用绑定同一对象，声明读/写权限和类型/形状。
- 引用本身不替代调用顺序，也不沿用旧块末数值控制边的交付规则。
- 数据生命周期统一管理，不能由每个引用者重复清零。
- 不把其它组件的任意私有字段直接暴露为无约束指针。

Task顺序调用与通用存储节点可以分期实现。
先将引用、参数调用和数值交付区分清楚，不要求第一阶段同时引入任意结构体或跨线程共享。
此前讨论及全局变量读写分析见[执行语义讨论](distillation-semantics-discussion.md)。

## 7. 框架变更面：不改具体模型

| 层 | 要完成的框架工作 |
|---|---|
| Project/Schema/加载 | 承载必要的新调用信息；旧工程兼容读取，不自动猜测缺失的函数调用流程 |
| 编译器/Plan | Source与Task绑定、显式驱动连接、实例与调用点分离、顺序/依赖校验、参数步骤及周期/相位信息 |
| Runtime | 按Task程序调用；仅在规定位置提交参数；共享错误/生命周期规则 |
| Generator | 从同一Plan生成可读Task函数；禁止另起一套顺序和提交时机 |
| 宿主/设备/DSP入口 | 一个Source的推进只进入对应Task一次；保留设备分块、停止和EOS处理 |
| UI/保存/API | 区分驱动、数据与参数/引用关系，表达必要的流程位置；保存/重载不丢失 |
| ABI/组件适配 | 优先保持现有process/set/get；新增调用能力确需ABI变更时版本化，不伪造兼容 |
| 测试/文档 | 用小型通用组件和合成工程验收，不让公司模型承担框架正确性测试 |

不修改ExperimentalModel的定义、分析账本、证明或布局来完成这次框架迁移。
已有蒸馏成果保留，后续是否按新能力迁移，是框架验收完成后的独立任务。

## 8. 兼容与建议分期

### 第一期：Source/Task驱动与明确顺序的最小闭环

- 确定新模式的版本/启用边界；旧工程和旧Plan保持原行为。
- 支持音频计算和仅驱动计算，贯通编译、Runtime、生成代码及必要的UI保存。
- 若旧工程缺少足以表达的新信息，保留旧模式或明确报告迁移要求，
  不能靠节点存储顺序、画布坐标或节点名称猜测原程序流程。
- 新Task程序不再叠加一份隐藏的旧拓扑调度或参数块末提交。

### 第二期：调用位置参数交换

- 同Task标量/BULK赋值与调用顺序一致。
- 外部写入按Task归属在安全点提交，不由无关Task入口提交所有实例的待写数据。
- 保持旧control_connections回归，提供明确的迁移和可视化语义。

### 第三期：控制结构、共享存储与跨Task合流

- 在相同内部调用模型上增加重复实例调用、条件和有界循环。
- 增加共享存储绑定/作用域及显式跨Task交付。
- 不以这一分期推迟第一期必须具备的单Task顺序正确性与双路径一致性。

分期是为缩小验收单元，并非把新模型宣称为已经实现；第一期若未提供新参数调用，
应明确保留其限制，不能声称已完整实现“按普通程序调用”的目标。

## 9. 定向验收矩阵

所有用例先比较独立参考，再比较动态与生成实现；不以双路径同错冒充正确。

| 用例 | 必须断言 |
|---|---|
| Source→A→B→输出 | 一次推进只调用Source及各步骤一次；输出与独立顺序程序一致 |
| Source驱动口驱动纯BULK计算 | 无音频样本消费要求；BULK槽顺序/shape不变；节点不被裁剪 |
| 同Task分支合流 | B/C完成后D恰好调用一次，无阻塞等待未执行分支 |
| 参数set→call | 后续调用本次即见新值，无额外一块延迟；旧模式仍保留旧行为 |
| BULK赋值→call | 真实typed数组本次生效；尺寸、类型、错误拒绝不被跳过 |
| 外部写入Task A | Task B入口不代为提交A的待写值；提交点可验证 |
| 多次调用同一实例 | 状态连续，调用次数正确；调用点与时间元数据不混同 |
| 每两次入口执行一次 | 继承周期和相位匹配；冷启动、跨块与reset后的计数正确 |
| 默认与显式频率契约 | 无特殊声明时输入输出同节拍；不同节拍依据显式声明传播校验，不从组件代码猜测 |
| 输入/输出不同交付频率 | 分别校验周期、相位及数据量；64帧两次输入后交付128帧，采样率不变且不重复交付旧buffer |
| 循环内每两次执行一次 | 每入口的调用次数与顺序正确，不误推导为等间隔独立Task |
| SPORT及多块长对齐 | 在共同帧时间轴推导重复窗口；另验相位、预填充和缓冲水位 |
| 条件跳过/reset/零处理量 | 按各自契约推进或保持状态，不隐式调用或清零 |
| 两Source/不同Task | Task独立推进；未经声明的共享调用/普通跨Task交付明确拒绝 |
| 保存/重载/复合展开 | 驱动绑定、实例身份、顺序和公开接口不丢失 |
| 旧工程/旧Plan | 原输出、周期、参数延迟及入口兼容；不做静默语义切换 |
| 停止/EOS/错误 | 生命周期调用次数、错误位置和已执行前缀明确；不误报成功 |

按实现单元选择对应测试，不重复跑公司模型的全部数值证明；
在集成里程碑再扩大回归。规则见[测试与验证](../10-testing.md)。
