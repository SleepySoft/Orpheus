# Source驱动的Task顺序调用：框架迁移设计

> 状态：框架迁移设计草案，2026-11-04。记录用户已明确的方向与建议实现边界，
> 不表示以下新能力已经落地。本次仅提交设计，不修改执行代码或具体模型/研究工程。
> 未经用户确认的字段名和分期均为建议，不是新的工程格式契约。

## 1. 已明确的方向

1. Task是代码的驱动者，Task内部按明确流程顺序调用组件。
2. 一个Source天然对应一个逻辑Task；Task不等于线程，不为每个Source强制创建线程。
3. Source继续通过普通音频流连出去，不新增一套Source分类或强制用户配置触发协议。
4. 只需要Task驱动的组件也接音频流，跟随其调用节拍，忽略样本数据；
   非音频计算不必伪装成音频计算，数组尺寸不因此变成音频时间长度。
5. 改动主体是框架：编译/Plan、Runtime调用、代码生成和参数交付。
   不修改公司算法、蒸馏叶子、具体研究工程或其布局来适配框架。
6. 工程描述/Schema、编辑器和兼容加载属于框架契约；若需要新增表达能力，
   应由框架提供并兼容旧工程，不要求用户逐个手改模型。

## 2. 为什么不是简单更换调度循环

当前已经具有：

- 工程Task及独立Task入口；
- Plan中的每Task执行顺序和局部周期；
- Runtime按顺序调用节点，生成代码按同一Plan展开；
- 同Task参数控制连接的块末两相快照；
- 跨Task音频的显式桥接。

参见[现有多Task实现](multitask-runtime.md)和[现有参数交付](control-links.md)。

因此，“把节点改成顺序调用”本身不是全新能力。需要改变/补齐的是：

- Source到Task入口的驱动关系明确化；
- 音频线同时可以只承载调用驱动，而不要求消费音频样本；
- Task调用流程成为可检查的执行事实，不再把任意原程序强行解释为一次拓扑遍历；
- 参数调用可以在Task内的指定位置执行；
- Runtime和生成路径对调用次数、顺序及状态使用相同定义。

统一静态调用顺序并不等于运行期全局协调。
例如`A(); B(); C(); D();`既是普通顺序程序，也是一份静态执行安排。
本次不是为了消灭所有“调度”概念，而是避免丢失明确调用流程。

## 3. Source与仅驱动的音频连接

### 3.1 驱动入口

```text
音频Source的一次有效推进
    → 对应Task入口
    → 顺序调用本次应执行的组件
    → 完成本次输出/显式交付
```

由宿主、设备回调或主动推进循环进入Task；Source的数据产生与Task执行不能
互相递归触发，也不能在同一次入口中把Source处理两次。
Source的“源组件”含义与manifest的`package_type: source`（源码包）无关，
后者不能作为创建Task的判断依据。

Task仍可由同一宿主串行调用，之后再按平台需要映射到线程、中断或外部任务。
外部节拍、主动推进及pacing继续沿用原术语，不新增第三种执行实现。

### 3.2 普通计算与仅驱动计算

```text
Source ─音频流→ 音频处理组件：处理样本并完成本次调用
Source ─音频流→ 仅驱动组件：完成本次调用，忽略样本
```

仅驱动连接的框架要求：

- 参与Task归属与本次调用关系，不因为样本无人读取就被裁剪。
- 不要求组件对音频做占位乘法、求和或复制。
- 不改变其已有BULK/参数端口的类型、形状和槽顺序；
  框架管理的驱动关联不能偷偷插入ABI输入数组，令旧组件的`inputs[0]`变成音频。
- 若组件已有可用音频输入，按声明绑定；若没有，由框架的编辑/编译层提供驱动接入能力，
  不逐个修改工程定制算法来补虚假的音频数据口。
- 音频块长决定驱动上下文，不决定频谱、参数表或历史数组的元素数。
- 不擅自跨越组件的enable、reset或其它条件：本次是否执行仍属于调用流程。

具体端口元数据/编辑器表示在实现阶段确定；这里不另引入用户必须理解的触发线类型。

## 4. Task内部调用语义

### 4.1 调用实例，不是复制实例

Task程序应能区分实例与调用位置：

```text
调用实例B
更新一项共享数据或参数
再次调用同一个实例B
```

第二次调用延续同一份实例状态，不能用复制一个节点冒充。
多次调用也不能仅靠在旧`execution_order`重复ID实现：
每个调用点的数据绑定、处理量、时间元数据与观测位置都必须明确。

建议在内部Plan中区分：

- 组件实例及其状态/资源；
- Task调用步骤及其顺序；
- 每一步的数据/参数访问与调用上下文。

这是一项内部表示建议，不要求立即在工程YAML中增加同名字段。

### 4.2 顺序、分支和循环

- 顺序明确时，直接执行顺序调用。
- 条件不满足时跳过调用，实例状态不被暗中推进。
- 循环重复的是指定调用步骤，不自动推进整个Task时间或复位状态。
- 每次Task入口只推进一次Task时间；组件调用时间如何对应样本区间须显式定义，
  不能无条件套用旧“每节点每周期一次”的时间公式。
- 实时循环需有可验证上界；不能把不受限的动态循环引入实时路径。

第一阶段不必同时开放所有控制结构，但不能宣称只增加一个顺序列表就已支持任意程序。

### 4.3 分支与合流

同Task内已明确执行`A → B → C → D`时，D在B/C之后运行，不另加等待节点。
只有按到达触发或跨Task交付的位置才需要显式合流/就绪规则。
同一串行Task中的首次到达不能阻塞等待尚未执行的分支。

不同Source的流程相遇时，不得悄悄把两个入口合成一个Task，
也不得由两个Task无保护地调用同一个有状态实例。
应显式确定接收Task、对应数据批次/时间区间及交付/触发方式；
跨Task数据面优先复用现有桥能力，不把音频驱动线直接当作共享可写内存。

## 5. 参数交换：区分调用与外部投递

以下是新Task调用模式的建议语义，不能静默套用到旧工程。

| 场景 | 建议生效规则 |
|---|---|
| 同Task的显式set/get或参数赋值步骤 | 在该步骤执行；后续调用看到新值，不默认延迟到下一块 |
| 外部UI/Bridge参数写入 | 排队到明确的Task入口安全点，由所属Task应用 |
| 跨Task参数/数组交付 | 显式消息、快照或桥；不得假定同一调用栈或共享地址立即可见 |
| restart_required或影响签名的配置 | 继续遵循重建/重启规则，不因顺序调用变成实时可改 |
| 旧control_connections | 保持旧块末快照语义，直到用户明确迁移 |

例如：

```text
set B.gain = 2
call B
```

必须在本次B调用前完成实际应用，包括组件参数回调、校验和必要的更新动作，
而非仅写入一个仍待下一块提交的控制bank。

标量与BULK都需要相同的调用位置语义；沿用现有类型、shape、策略和错误检查。
数组型参数不因数据大就必须改成引用；共享引用也不能冒充参数setter，
绕过组件的状态一致性或系数更新动作。

一组需要原子生效的参数应以明确事务/调用步骤描述；不得自动把若干独立写入视为原子。
调用失败立即返回错误，不继续执行依赖该写入的后续步骤；
已发生的计算或状态修改不承诺回滚，错误位置必须可定位。

## 6. 共享数据与控制连接的边界

通用存储模块/数据buffer节点仍是候选能力：

- 存储可属于工程/子系统，不必属于某个计算节点。
- 引用连接或命名引用绑定同一对象，声明读/写权限和类型/形状。
- 引用本身不替代调用顺序，也不沿用旧块末数值控制边的交付规则。
- 数据生命周期统一管理，不能由每个引用者重复清零。
- 不把其它组件的任意私有字段直接暴露为无约束指针。

Task顺序调用与通用存储节点可以分期实现。
先将引用、参数调用和数值交付区分清楚，不要求第一阶段同时引入任意结构体或跨线程共享。
此前讨论及全局变量读写分析见[执行语义讨论](distillation-semantics-discussion.md)。

## 7. 框架变更面：不改具体模型

| 层 | 要完成的框架工作 |
|---|---|
| Project/Schema/加载 | 承载必要的新调用信息；旧工程兼容读取，不自动猜测缺失的函数调用流程 |
| 编译器/Plan | Source与Task绑定、仅驱动连接、实例与调用点分离、顺序/依赖校验、参数步骤及时间信息 |
| Runtime | 按Task程序调用；仅在规定位置提交参数；共享错误/生命周期规则 |
| Generator | 从同一Plan生成可读Task函数；禁止另起一套顺序和提交时机 |
| 宿主/设备/DSP入口 | 一个Source的推进只进入对应Task一次；保留设备分块、停止和EOS处理 |
| UI/保存/API | 表达驱动接入和必要的流程位置；保存/重载不丢失，不把引用误画成跨块参数投递 |
| ABI/组件适配 | 优先保持现有process/set/get；新增调用能力确需ABI变更时版本化，不伪造兼容 |
| 测试/文档 | 用小型通用组件和合成工程验收，不让公司模型承担框架正确性测试 |

不修改ExperimentalModel的定义、分析账本、证明或布局来完成这次框架迁移。
已有蒸馏成果保留，后续是否按新能力迁移，是框架验收完成后的独立任务。

## 8. 兼容与建议分期

### 第一期：Source/Task驱动与明确顺序的最小闭环

- 确定新模式的版本/启用边界；旧工程和旧Plan保持原行为。
- 支持音频计算和仅驱动计算，贯通编译、Runtime、生成代码及必要的UI保存。
- 若旧工程缺少足以表达的新信息，保留旧模式或明确报告迁移要求，
  不能靠节点存储顺序、画布坐标或节点名称猜测原程序流程。
- 新Task程序不再叠加一份隐藏的旧拓扑调度或参数块末提交。

### 第二期：调用位置参数交换

- 同Task标量/BULK赋值与调用顺序一致。
- 外部写入按Task归属在安全点提交，不由无关Task入口提交所有实例的待写数据。
- 保持旧control_connections回归，提供明确的迁移和可视化语义。

### 第三期：控制结构、共享存储与跨Task合流

- 在相同内部调用模型上增加重复实例调用、条件和有界循环。
- 增加共享存储绑定/作用域及显式跨Task交付。
- 不以这一分期推迟第一期必须具备的单Task顺序正确性与双路径一致性。

分期是为缩小验收单元，并非把新模型宣称为已经实现；第一期若未提供新参数调用，
应明确保留其限制，不能声称已完整实现“按普通程序调用”的目标。

## 9. 定向验收矩阵

所有用例先比较独立参考，再比较动态与生成实现；不以双路径同错冒充正确。

| 用例 | 必须断言 |
|---|---|
| Source→A→B→输出 | 一次推进只调用Source及各步骤一次；输出与独立顺序程序一致 |
| Source音频线驱动纯BULK计算 | 无音频样本消费要求；BULK槽顺序/shape不变；节点不被裁剪 |
| 同Task分支合流 | B/C完成后D恰好调用一次，无阻塞等待未执行分支 |
| 参数set→call | 后续调用本次即见新值，无额外一块延迟；旧模式仍保留旧行为 |
| BULK赋值→call | 真实typed数组本次生效；尺寸、类型、错误拒绝不被跳过 |
| 外部写入Task A | Task B入口不代为提交A的待写值；提交点可验证 |
| 多次调用同一实例 | 状态连续，调用次数正确；调用点与时间元数据不混同 |
| 条件跳过/reset/零处理量 | 按各自契约推进或保持状态，不隐式调用或清零 |
| 两Source/不同Task | Task独立推进；未经声明的共享调用/普通跨Task交付明确拒绝 |
| 保存/重载/复合展开 | 驱动绑定、实例身份、顺序和公开接口不丢失 |
| 旧工程/旧Plan | 原输出、周期、参数延迟及入口兼容；不做静默语义切换 |
| 停止/EOS/错误 | 生命周期调用次数、错误位置和已执行前缀明确；不误报成功 |

按实现单元选择对应测试，不重复跑公司模型的全部数值证明；
在集成里程碑再扩大回归。规则见[测试与验证](../10-testing.md)。
