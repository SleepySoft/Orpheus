## 1. 原始设想与核心问题

用户设想：

- 算法也是普通程序，函数可以对应组件，实例对应节点。
- 一系列共同完成目标的函数，可以封装为包含子节点的复合节点。
- 函数调用转为节点连接；FIR、IIR、FFT等成熟计算优先复用标准组件。
- 因而，按调用层次自顶向下蒸馏理应较直接，但实际成本明显超出预期。

需要解释的不是“为什么缺少某几个组件”，而是上述映射遗漏了什么信息。

初步分析：

> 函数调用图描述“谁调用谁”；可执行图还必须保留数据、状态和执行控制。
> 调用不只是传数据，也可能读写共享存储、按顺序修改状态、条件执行或重复执行。

纯函数`y = square(x)`通常能直接转换为输入→平方节点→输出。
有状态计算还需要表达：

```text
（输出，新状态） = F（输入，旧状态，本次参数）
```

以及该计算的执行条件、次数、顺序和输入数据的新旧关系。
这些语义可以由图显式表达，也可以封装在组件内部；不意味着每个if/for都必须画成节点。

## 2. 用户修正：公司算法的数据统一存放于全局区

用户明确的前提：

> 公司的算法中数据都是全局变量，在所有阶段都有访问。
> 因此应该不存在共享状态难表达的问题；唯一的问题是暂不确定什么全局变量会被哪个步骤改变。

对“共享状态”这一项，应据此修正此前表述：

- 不应预设原算法的状态必须拆成每个节点独占的一份，更不能据此推导“函数映射节点天然困难”。
- 在统一全局数据区的前提下，同一个状态对象可以由多个步骤访问；
  “多个步骤共享同一对象”本身不是不可表达的语义。
- 当前真正需要补齐的是各步骤的读写集合、访问条件及先后关系：
  谁修改了哪一项，后续步骤读取的是修改前还是修改后的值。
- 这种“不确定”首先是分析结果尚未建立，不应直接解释为算法运行时本身不确定，
  更不能未经证据就假定存在并发、竞争或需要加锁。

因此，针对共享状态，更准确的gap是：

> 不是“共享状态无法表达”，而是“尚未建立全局数据访问与更新时序的显式模型”。

这条修正针对共享状态问题，不表示其余调用条件、执行频率和数值等问题已经讨论完毕。
后续应逐项确认，不能把先前分析整体当作已达成共识。

### 2.1 最小实例：共享对象明确，读取版本仍取决于顺序

```c
float global_value;
float output;

void stage_a(void) { global_value = 1; }
void stage_b(void) { global_value += 2; }
void stage_c(void) { output = global_value; }
```

| 执行顺序 | stage_c读到的值 |
|---|---:|
| A → B → C | 3 |
| A → C → B | 1 |

没有必要把global_value复制成三份节点私有状态。
需要记录的是：A写入，B先读后写，C读取，以及三者的真实执行顺序。
如果B未执行，C应读取已保留的全局值，而不是凭空产生一个“本次B输出”。

此前“同一个累加函数被两个节点各自实例化，导致共享累计变成独立累计”的例子，
说明的是错误地复制状态会改变行为；它不能作为公司算法的共享状态本来就难表达的证据。

### 2.2 后续可讨论的分析记录

以下是候选分析格式，不是已决定要增加的新框架接口：

| 记录项 | 示例内容 |
|---|---|
| 全局对象/区域 | 某结构体字段、数组区间、同一底层存储的别名 |
| 读取步骤 | 哪个函数/调用位置读取，是否先读后写 |
| 写入步骤 | 谁写入、覆盖还是累积、是否只修改部分区间 |
| 执行条件与顺序 | 总是执行/使能时执行；先于或后于哪些步骤 |
| 值的延续 | 读取本轮写入值还是之前保留值；未执行时是否保持 |
| 初始化与复位 | 谁初始化、何时初始化、复位哪些区域 |
| 来源索引 | 文件、函数、行号及直接/间接访问的证据 |

“全局区”是存储事实，不等于每个函数都读写整个全局区。
分析需落到实际字段/区间；通过指针或被调用函数发生的间接写入也要计入。
若原执行顺序已确定，应优先保留，不因没有普通数据线依赖就随意重排。
如何在Orpheus中承载这份共享数据与顺序关系，留待后续讨论，不能先假定必须改变存储模型。

## 3. 其余初步gap与实例：保留待讨论

以下延续前次回答，仅作讨论素材，不是要求用户一次性接受所有结论。

### 3.1 参数调用的发生时机

```c
set_gain(filter, 2);
y = process(filter, x);
```

原顺序表示本次处理就使用新参数。若转为块末提交的参数连接，
就可能下块才生效。缺失的是调用先后和生效时机，而不是乘法组件。
若参数本来就在全局区，应检查设置步骤何时写、处理步骤何时读。

### 3.2 条件执行与条件选择不是同一件事

```c
if (enabled)
    y = delay_process(x);
else
    y = x;
```

如果延迟节点始终执行，只在末端选择干声，则停用期间历史仍推进，
重新启用时不同于原程序。应保留“该分支未调用，因此状态未更新”的事实。
本阶段pool_delay已补齐停用干声且冻结整个共享池/游标的契约。

### 3.3 同一全局池的读写顺序

```text
先读取全部通道旧池，再统一写入全部通道
```

不一定等价于：

```text
逐通道读取，立即写入，然后处理下一个通道
```

若写入区与后续读取区重叠，后者会过早读到新数据。
这也是全局对象的读写集合与顺序问题，并非共享池本身不可表达。

### 3.4 首次初始化也是状态更新步骤

HF噪声保持的实际边界是：先交付当前输出并提交快照，最后才首次初始化地板。
把初始化提前会改变第一次输出；分析全局变量时需要把初始化步骤一并纳入，
不能仅罗列稳态数学公式。

### 3.5 数据尺寸不等于时间含义

同样是256个float，可以表示连续音频采样、频域数组、参数表或历史切片。
估计器每4块更新一次、消费者每块读取时，还需明确是否读取最近值。
指针类型和长度本身不足以回答这些问题；其在当前模型中的具体处理留待讨论。

### 3.6 数学等价与浮点逐位等价

标准DSP组件解决数学计算核，但替换实现可能改变浮点运算顺序。
逐位等价是一项严格验收标准，不是蒸馏天然必须采用的唯一标准。
允许误差的定义应与状态/时序等价分开讨论；放宽浮点误差不能弥补错误的状态更新。

## 4. 当前讨论结论与边界

- 用户的模块化、分层和标准组件复用方向不因上述分析而被否定。
- 已明确修正共享状态论点：在用户给定的全局数据模型中，应先建立读写与更新顺序，
  而不是把节点私有状态当作必须接受的原始前提。
- 函数、调用、意图和源码索引之外，需要补充哪些执行信息，仍按上述问题逐项讨论。
- 不能把每个叶子重复调查语义、临时搭建对拍的工程成本，全部归因于算法本身困难；
  已知信息应持久记录并复用。
- 本次仅记录讨论，不继续蒸馏、不修改框架，也不变更现有验收标准。
