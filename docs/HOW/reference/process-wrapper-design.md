# 处理调用 Wrapper 与有界调用统计树

> 状态：2026-11-10 讨论收敛后的设计记录，尚未实现。
> 本文不修改组件链式调用语义，不实施统计树、bypass 或噪声检测。
> 设计名称和阶段名不是现有 API；内存数字是布局预算，不是实测结果。

## 1. 目标与适用范围

所有 Task 驱动执行链上的组件 `process` 经过统一、可扩展、可配置的 wrapper，
允许系统在调用前、输出交付时及调用结束后工作，但不决定组件何时续调下游。

- 包括音频 Source、无音频 Task Source、分频驱动的组件、控制计算、Buffer 和链路终点。
  范围按“是否实际进入处理调用链”划分，不按“是否有音频端口”划分。
- Task 入口建立根上下文，不因此把 Task 变成新的普通图节点。
- `create/prepare/reset/destroy`、参数读写、资源注册、控制通信不进入这套 wrapper。
  将来需要生命周期或通信拦截时单独定义，不混入处理调用统计树。
- 这些操作若发生在被测调用内部，时间仍会计入相应跨度；“不包装”不等于计时器
  能自动剔除其中的耗时。
- Runtime 和生成 C 必须使用相同的阶段、能力校验、错误传播和统计定义。
  不保留一条绕过 wrapper 的产品执行路径，也不改回调度器逐节点遍历。

## 2. 已核实的当前基础

实现依据：

- [ABI](../../../orpheus_abi/include/orpheus_abi.h)：统一
  `process(void* state, const OrpheusProcessContext* ctx)`；
  `ctx` 包含端口 Buffer、帧数、采样率、时间线和 `continuation`。
- [共享链式执行](../../../orpheus_abi/include/orpheus_chain.h)：
  `OrpheusChainRun` 在同次同步链上共享；
  `orpheus_chain_continue` 先发布，再按连接顺序调用直接下游。
- [Runtime](../../../orpheus_runtime/src/runtime.cpp)：
  `invoke_chain` 按实例绑定构造本节点的局部 `ctx`，然后调用接口表中的 `process`。
- [生成器](../../../orpheus_core/orpheus_core/generator.py)：
  `_generate_chain_scope` 生成逐节点入口适配，复用同一链式执行实现。
- [Gain](../../../components/orpheus/builtin/gain/src/gain.c)：
  `prepare` 从配置数组读取参数并保存到实例；`process` 读取实例和 Buffer，
  最后显式调用 `orpheus_process_next`。

所以，A 调 B 时既不是传递一份任意算法形参列表，也不是复用 A 的整个 `ctx`：
B 有自己的状态和端口绑定，适配入口为 B 构造新 `ctx`。
普通数据边引用预绑定 Buffer，桥接数据按既有规则发布。

当前没有本文的可配置处理 wrapper、调用统计树和完整共享统计上下文。
ABI 接口表已有的 `hook(state, id, event, req, resp)` 属于控制消息扩展，
不复用为逐次处理调用 hook，避免协议语义和实时开销混杂。

## 3. 统一入口与最小侵入

wrapper 放在框架的组件调用边界，而不是要求每个算法手工包住函数体。
Runtime 和生成入口完成上下文准备后，通过同一公共 C 实现调用原始 `process`。
仅平台计时等底层能力由平台提供，阶段控制不在两条执行路径各复制一套。

```text
Task 建立共享执行上下文
  → 本节点入口适配：准备参数、桥接输入和局部 ctx
  → 公共 wrapper
      → 原始组件 process / 明确支持的 bypass 处理入口
          → continuation：发布 → 输出观测 → 直接下游入口
              → 同一个公共 wrapper
      → 调用结束收尾
```

- 实例地址、原始函数指针、稳定实例 ID、能力及生效策略在初始化时绑定。
  实时阶段不查组件名、不解析字符串、不构造通用动态参数包。
- 默认组件不需要为统计修改算法代码；已有 `orpheus_process_next/branch` 保持原样。
- 若组件需要声明专用 bypass 等能力，可用一行宏注册其描述和强类型函数指针；
  宏只做薄声明，不能把状态机或钩子逻辑展开到所有组件。
- 组件接口表保留原始处理入口；不同时采用“接口表已包装”和“调用方再包装”，
  避免同一次调用被计数两次。算法单元测试可以直接调用原始入口；
  产品 Task 调用和续调不能旁路公共入口。
- 不包装算法内部普通辅助函数，不把每个乘加变成树节点。

## 4. 三种时刻：进入、输出交付、整次调用结束

不能把“调用后”当成唯一钩子。A 的 `process` 可以在中间同步调用 B，
待 B 及其下游全部返回后，A 还可以继续计算或再次续调。

### 4.1 进入与结束

1. Task 入口固定本次生效策略，建立根上下文。
2. 节点入口按既有顺序完成目标参数/BULK 更新、桥接输入读取、端口与时间线准备。
3. wrapper 进入：建立本次统计帧，按策略读取或计算输入观测。
4. 只选择一个处理入口：正常 `process` 或专用 bypass。
5. 处理入口返回后执行结束钩子，记录返回码、耗时并恢复父上下文。
6. 错误返回同样必须收尾；不能因提前返回而泄漏“当前父节点”或统计深度。
   ABI 禁止异常跨越处理边界，不以捕获异常代替正常错误协议。

输入观测必须在算法或旁路改写原地 Buffer 之前完成。结束钩子用于调用统计、
状态摘要等，不能假定此时仍能读取“刚刚由 A 产生、尚未被下游改写”的音频。

### 4.2 输出交付

在每次有效 `orpheus_process_next/branch` 中，保持以下顺序：

```text
组件写好输出 → 既有发布逻辑成功 → 输出观测 → 调用选中的下游
```

- 观测读取当前发布端口，且必须先于任何下游原地处理或 Buffer 复用。
  必要音频快照在此时复制到预分配槽，不把借用指针留给后台线程。
- 每次续调是一次交付事件。重复续调可产生多次输出观测；
  一次 `next` 的多个兄弟分支不为同次交付重复执行输出观测。
- 分频后没有实际下游调用，仍可能有一次发布；分别记录交付次数与实际调用次数，
  不把二者当作同一个指标。
- 发布失败沿原调用链返回，不调用下游；记录失败阶段，不能伪装成一次成功交付。
- 零下游时仍可通过 `next` 发布和观测。组件不调用续调便只表示停止传播；
  wrapper 不在返回时偷偷发布、补调下游或把旧输出解释为本次新输出。
- 若组件以后需要“不续调但显式提交输出”，应增加独立且明确的提交契约，
  复用同一输出观测阶段；不能通过猜测 Buffer 内容是否变化实现。

端口观测必须遵循该端口的类型、布局、容量及本次有效帧数，不能把
`ctx.frame_count` 无条件套到所有输出上。当前上下文没有完整的逐次交付身份：
涉及循环内不同片段或异频端口时，后续能力须显式提供有效视图和时间/序列信息，
不能声称仅靠现有 `frame_count` 已能精确配对所有输入输出。

## 5. Task 根与上下文连续传递

设计上的共享执行上下文包含：入口身份、本次调用序号、采样决定、生效策略、
统计存储引用、当前父路径及统计深度。概念上由 Task 创建，随本次同步调用返回销毁；
累计统计存储则跨调用保留。

- 优先在 `OrpheusChainRun` 中携带显式上下文指针，continuation 继续持有该 `run`，
  每个节点适配入口把同一指针交给公共 wrapper。组件继续拿自己的局部 `ctx`；
  不要求算法自己压栈，也不必先给公共 `ProcessContext` 增加 `execution` 字段。
- 续调进入子节点前显式设置调用边身份，返回时连同父路径恢复；
  Task 直接入口也有稳定入口边身份，不从被调组件自身计数反猜调用者。
- 不使用进程全局 `current_task/current_node`，也不以 TLS 隐藏传参关系。
  未来若确需改变组件公共 ABI 布局，应明确提升 ABI 并统一重建，不静默混用旧 DLL。
- 一个宿主实际启动的逻辑 Task 是一棵根；同一次根调用里的分频边不是新根。
  派生执行若真被注册为独立 Task、由宿主另行启动，则使用自己的根。
- 同一 Task 的多个直接入口是根下的兄弟，返回后恢复根；不让第二个入口误挂到第一个下面。
- 当前全局 `process_block` 使用全局链，不携带具名 Task 身份。
  在该入口记录时必须明确标为全局入口作用域，不伪造其 Task 归属；
  不将它与具名 `process_task` 的统计混成一棵树。
- 跨 Task 的 Ring Buffer 只传数据与约定元数据，不传栈上的上下文指针。
  目标 Task 自己建立根；需要跨 Task 因果关联时另加关联 ID，而非延长同步调用栈。
- 每个执行流独立拥有活动上下文和写入存储。不能因增加 wrapper 就允许同一实例、
  同一 Task 累计树被多个线程或中断并发修改；同 Task 重入必须明确拒绝或配置独立执行槽。
- 图实例重建后建立新的统计会话；快照携带图身份、会话/策略版本、时钟单位、
  采样与截断信息，不用重建前的实例索引解释新图数据。

## 6. 有界聚合路径树，而非逐调用日志

树按实际调用路径聚合，键至少包括：

```text
入口根 + 父路径记录 + 稳定调用边 ID + 被调用组件实例 ID + 实际处理模式
```

同一边的循环调用、重复续调只累加，不追加事件记录。
同一父组件到同一目标的不同调用边仍可区分，不能仅按组件 ID 把调用图误称调用树。
正常与旁路使用不同模式记录，模式位可存于记录标志；两者都消耗同一个有界路径池，
不以切换旁路为由无限创建历史版本。
复合组件使用展开后的完整实例身份，显示名称通过只读字典解析，不在每条记录存字符串。

例如 `A → B → D` 和 `A → C → D`，树上两个 D 分别统计；
不增加会合屏障、不去重、不等待另一分支。边分频未命中不建立虚假的被调调用。

### 6.1 计数与计时口径

- 每条路径记录观测到的调用次数、失败调用次数、包含耗时累计/最大值、
  自身耗时累计/最大值。祖先的失败计数表示返回失败，不等于又发生一个独立根因。
- 包含耗时覆盖本次 wrapper 进入到退出，包括同步下游。
  自身耗时 = 包含耗时 − 本次所有直接子 wrapper 的包含耗时之和。
- 自身耗时仍包括本层钩子、发布、下游入口准备等未落入子 wrapper 跨度的框架开销，
  以及下游返回后的本层工作；不能标成“算法净 CPU 耗时”。
  Task 根还可单列入口准备、块末工作等未落入组件跨度的时间。
- 默认计时器是平台单调时间/周期计数，不保证是线程 CPU 时间。
  抢占或中断会增加被中断调用的跨度；独立 Task 的墙钟统计不可直接相加当作总 CPU 用量。
- 所有同步帧使用同一时钟，声明频率、精度与回绕处理；无可用时钟时不允许启用计时能力。
  时钟异常、累计溢出或无法完整扣除子耗时必须打有效性/溢出标记，不静默截成零。
- 不保存逐调用样本，因此基础树不能给出精确 p95/p99；直方图等是另行预算的可选能力。

采样以整次 Task invocation 为单位决定；被采中的一次执行覆盖其全部实际子调用，
不能只计父而随机漏掉子，再宣称自身耗时准确。界面应显示采样率和
“采样调用次数”，不将其冒充全部实际调用次数。
噪声观测等功能有独立策略，不因统计采样关闭而意外失效。

### 6.2 内存预算与溢出

固定容量路径池和固定深度统计栈在初始化时预分配；沿父记录查直接子记录，
可以先用有界兄弟链表，不默认增加哈希表。查找最坏开销也要计入实时预算。

一个可核算的示例记录布局为：

| 字段组 | 字节 |
|---|---:|
| 父、首子、下一兄弟、调用点索引，各 `uint16_t` | 8 |
| 调用数、失败数、包含/自身累计、包含/自身最大值，各 `uint64_t` | 48 |
| 标志和保留字段 | 8 |
| 合计 | 64 |

调用点字典将稳定调用边和目标实例绑定，避免在记录内遗漏用于区分路径的边身份；
实际处理模式存于标志位。该示例使用 16 位索引并预留无效值，
容量与调用点字典必须遵守其上限；
正式实现用编译期布局断言核实，不把预算当成所有目标 ABI 的保证。
此前讨论的 48 B/节点仅是粗估，这里将索引、失败计数和标志计入后按 64 B 预算。

- 每 Task 256 条记录约 16 KiB；32 层统计栈按每帧 24 B 估算约 768 B。
- 另计 Task 上下文、实例/边 ID 字典、检测器状态、音频快照及导出槽。
  总预算按所有 Task/执行槽相加，不能只报一棵树的大小。
- 树满或统计深度满只截断统计，不影响实际处理、发布与续调。
  未跟踪子树不得误挂到祖先；必须恢复父上下文并报告截断计数。
  若无法保留完整子耗时扣除，则相应自身耗时标为不完整。
- 统计深度限制不是 C 调用栈保护，也不是循环合法性检查；
  wrapper 不为无限递归提供安全承诺，不改变现有图合法性规则。

### 6.3 导出与线程安全

默认先支持停机读取；在线导出是可裁剪能力。
实时写者只在明确的 Task 安全边界处理快照请求，向预分配的空闲导出槽复制。
读者只读已发布且已获得所有权的不可变槽，读完释放；槽所有权/发布使用
目标平台支持的原子协议，禁止读取正在写的累计字段。

没有空槽时丢弃本次导出并计数，不等待 UI，不覆盖读者持有的数据。
不能用“读到一半再检查序号”替代 C/C++ 内存模型下的数据竞争保护。
复制成本有固定上界，降频执行并纳入 Task 耗时。

若每份快照复制整个路径池，256 条记录的一个导出槽另需约 16 KiB；
活动树加一个槽约 32 KiB，加两个槽约 48 KiB，均还未包含上述其他内存。
不需要在线导出时不付这部分内存。
清零/切换统计区同样通过执行流边界请求，不允许外部线程直接清写活动树。

## 7. 功能配置与扩展契约

配置分三层，具体 YAML/API 字段在实施时定义，本次不提前发布 schema：

1. **构建能力**：是否包含计时/路径树、端口观测、专用 bypass。
   不编译的功能同时裁掉代码、分支与存储；全关时仅剩可内联的原始调用。
2. **组件能力**：支持哪些端口视图、旁路处理入口和状态策略。
   无声明不猜测，不把“不支持”当成“已启用但什么也没做”。
3. **实例策略**：对哪些实例/端口启用何种已构建能力、统计采样率、检测预算等。
   请求未构建或不支持的能力在加载/配置时显式拒绝并定位实例。

运行期配置由所属 Task 在边界接收预验证、预分配的策略快照，
同次 invocation 内保持一致，不能父节点按旧策略、子节点临时换新策略。
不在处理线程解析配置或执行任意用户脚本。
以后若支持处理中途改变旁路等行为，须另行设计可重复的生效边界，而非读可变全局开关。

各阶段采用固定顺序、只读视图和明确能力的回调，不允许观测扩展任意改写音频、
调用下游、改变浮点控制模式或改变错误码。需要改变执行语义的功能必须像 bypass 一样单独声明。
检测状态与统计树分开预算；不因调用路径增多就隐式复制完整检测器状态。

初始化和配置失败按现有错误通道报告。运行期观测丢帧、预算不足或检测器不可用
记录明确状态/计数，由非实时 Adapter 上报，不把观测缺失伪装成“无噪声”。
被动观测默认不改变原始处理返回码；若未来需要故障停机策略，须显式配置并另行验证。
算法和发布错误继续原样向上传播，已执行组件不回滚，未执行的兄弟不补跑。

## 8. Bypass 不等于“不调用 process”

当前续调由组件自己控制，所以跳过 `process` 后再由 wrapper 自动 `next`
既可能漏掉输出，也可能改变分支、循环和分频语义。

- Bypass 是替代处理入口：正常入口和旁路入口二选一，旁路入口负责明确的数据映射、
  输出有效信息以及应有的续调；二者都处于同一个 wrapper 生命周期内。
- 简单直通仅适用于端口映射、格式、布局、通道数、帧数、速率和时序均明确匹配的组件。
  不能默认复制第一个输入到所有输出。
- Source、分频/条件分支、组拆块、采样转换、状态交换和异步桥默认不支持通用旁路；
  需要时组件提供专用语义，不能绕掉节拍或 Ring Buffer 协议。
- 每种旁路能力声明状态策略：冻结、仍更新或恢复时重置。
  “仍更新”须提供专用支持，不能先调用会续调的原始 `process` 再调用旁路导致双调。
  重置/平滑切换若非实时安全，则停机或在预先允许的控制阶段处理；
  不能在 wrapper 中直接调用未经声明的 `reset/prepare`。
- 开关只在所属 Task 约定边界生效；恢复时是否无爆音需组件专门保证。
  统计须区分正常与旁路调用，检测器清楚标记当次实际路径。

## 9. 输入/输出质量检测

wrapper 仅提供准确取样时机、端口描述和有界存储，不内置一个适用于所有组件的
“噪声算法”。首批可选择 RMS、Peak、非有限值或削波检查；
它们不是噪声底或信噪比的同义词。

- 噪声估计必须声明参考信号、静音/语音假设、窗口和阈值；
  输入输出比较显式指定配对端口及时间对齐，不能默认同下标、同帧长就是同一时刻。
- 检测只处理选定的有效端口，按帧数/通道数配置预算，不强制复制整块数据。
  数据缺失、格式不支持与检测失败是独立状态，不输出成功形状的零值。
- 交付事件数不等于唯一音频块数。重复续调同一数据时，
  有状态检测器不能仅按事件次数推进采样时间；需要明确的片段序列/时间元数据，
  不支持这些元数据的组件不能启用依赖精确连续时间的检测模式。
- 有状态检测器明确处理 epoch/不连续事件；重置检测器自身的状态不意味着
  wrapper 可以重置被观测算法组件。
- 本次进入的输入与多次交付的输出不一定一一对应。
  质量指标按各自事件/片段记录，不强行生成误导性的“一进一出差值”。
- 参与算法控制、触发旁路或改变增益的分析不再是被动观测，
  应显式作为算法/控制策略设计，不能偷偷通过观测钩子改变音频。

音频、统计和告警最终交给现有 Observation/Access Bridge 分层的非实时导出端。
wrapper 内禁止堆分配、阻塞锁、IO、日志打印和异常传播。
hook 是额外计算开销，不能以“只有一行宏”宣称零开销。

## 10. 案例推演与后续验收

| 情形 | 约定结果 |
|---|---|
| `A → B → C` | 三次实际调用、三帧嵌套；每次结束都恢复父帧 |
| `A → B → D`、`A → C → D` | D 执行两次，分别归于 B、C 路径；不引入会合规则 |
| B 原地修改 A 的输出 | A 的输出观测发生在 B 之前，不读取 B 修改后的值冒充 A 输出 |
| A 循环中三次调用同一续调 | A 一次调用、三次交付；同一路径的下游计数累加，不无限建树 |
| 一次 `next` 含多个兄弟分支 | 先观测一次交付，再依序调用实际命中的分支 |
| 调用边分频未命中 | 不统计虚假的下游调用，不由统计功能补跑 |
| A 不续调而成功返回 | A 计数/收尾，下游不执行，不自动发布或检测旧输出 |
| 下游失败或发布失败 | 各已进入帧正常收尾，错误原样传播，后续兄弟不执行 |
| 同一 Task 有多个入口 | 都挂在 Task 根下，不互相误当父子 |
| 异步桥连接另一个 Task | 只交付数据；目标另起上下文，不保留来源栈指针 |
| 路径池/深度/导出槽耗尽 | 音频与调用顺序不变；截断/丢弃显式可见，统计有效性明确 |
| 旁路无能力或配置不匹配 | 配置阶段拒绝，不假装启用，不猜端口映射 |
| 合法旁路启用后关闭 | 每次只进一个入口，按已声明的状态恢复策略处理 |
| Task 被抢占、同实例跨 Task 使用 | 墙钟口径明确；不据 wrapper 推导线程安全或净 CPU 用量 |
| wrapper 能力全关 | 调用、错误、发布、状态与音频逐字节结果均保持原语义 |

计时算例：A 为 `[0,15]`，直接子 B 为 `[2,7]`、C 为 `[8,12]`，
B 的子 D 为 `[3,5]`。包含耗时分别为 15、5、4、2；
自身耗时分别为 6、3、4、2，总和为 15，不重复累加 D。
重复调用时逐帧扣除后累加，而不是用聚合树上的祖孙累计值反复相减。

后续实施按以下顺序拆分，不一次引入全部功能：

1. 公共 wrapper、共享上下文、进入/交付/结束阶段；先用测试回调验证顺序和错误收尾。
2. 固定容量路径树、整次 Task 采样和停机读取；核实实际布局与计时器成本。
3. 可选在线快照与 Adapter 导出，覆盖所有权、饥饿和清零边界测试。
4. 分别实施选定质量检测器与有能力声明的组件旁路，不默认给所有组件开启。

每阶段都验证动态/生成路径的调用轨迹、返回码、状态与音频结果一致；
覆盖上表并测量不同块长、链深、分支、采样率下的最坏开销。
能力全关、仅计数、计时、输出观测和在线导出分别报告增量 CPU、内存及原生调用栈，
不能只验证“编译通过”，也不在实测前承诺具体性能阈值。

结论：统一处理 wrapper 与现有自主续调模型没有结构性冲突。
关键修正是把“输出交付”与“整次调用结束”拆开，并明确统计容量、采样、
所有权和旁路能力；平台成本和各组件能力仍需在实施时以测试和测量验收。

## 11. 实践反思：AWE 集中执行与组件自主续调

> 2026-11-10 补充。此节记录搭建框架、推演 wrapper 并追踪画布调用语义后暴露的
> 取舍，不表示决定改回集中执行，也不表示已经实施执行流可视化。

### 11.1 AWE 的执行模型与普通连线

依据 AWE 官方架构说明中 Wire Buffers、Layouts、Multithreaded Processing 和
ChangeThread 各节：

- 普通 Wire 对应内存中的信号 Buffer，携带格式、通道数、块长和采样率等信息。
  构建时按信号依赖确定模块执行顺序，输入输出 Buffer 预先绑定并可按生存期复用。
- Layout 是按执行顺序排列的模块集合。运行时引擎遍历该有序集合，调用各模块的
  处理函数，不是 A 经普通 Wire 直接调用 B。
- 多线程处理中，Layout/线程和 clock divider 定义不同执行节拍；
  ChangeThread 等机制可向下游传播线程属性。可以类比“Task 拥有一组处理模块”，
  但不能将 Layout 无条件等同于 OS Task，也不能概括为纯手动把模块拖进任务。
- 普通信号线还可携带每块一个数值的控制信号。计算输入/控制信号与可调模块变量
  是不同概念，不能把普通 Wire 都解释为 `set_parameter`。

因此，“连线表征数据及上下游，构建阶段编排顺序，运行时引擎依次执行”
是对这个模型的有效概括。数据连线影响执行编排，但不是运行时调用权的传递。

来源：

- [AWE Architecture](https://dochub.dspconcepts.com/latest/audio-weaver-architecture/AWEArchitecture/)：
  Wire 与 Layout、执行顺序、线程切换，以及 Active/Bypassed/Muted/Inactive 的处理。
- [Audio Weaver Module Basics](https://dochub.dspconcepts.com/latest/audio-weaver-modules/ModuleBasics/)：
  可调变量、Inspector 与 `blockSize = 1` 控制信号的区别。

### 11.2 两种模型的取舍

| 维度 | AWE 所代表的集中执行模型 | Orpheus 当前自主续调模型 |
|---|---|---|
| 执行权 | 引擎按已编排的模块列表调用 | Task 启动入口，组件决定是否、何时及多少次续调 |
| 普通连线 | 信号 Buffer 与依赖，参与执行编排 | 数据 Buffer；端口与入口声明可派生调用关系，但写输出本身不触发下游 |
| 普通组件责任 | 计算本模块输出并返回 | 计算输出，并在合适位置显式续调或停止 |
| 条件、循环、多次交付 | 若影响后续执行，需要引擎或图模型表达相应控制语义 | 可由组件控制续调分支和次数，但不意味着允许任意循环图 |
| 统一观测与旁路 | 引擎拥有每次调用边界，容易统一插入；特殊组件仍可能需要专用旁路 | 需同时掌握进入、交付与嵌套返回边界，旁路不得破坏组件续调语义 |
| 用户理解成本 | 显式展示归属和执行顺序后，容易回答“谁执行、按什么顺序执行” | 若只展示数据端口和驱动归属点，用户难以判断实际调用关系 |

这不是简单的先进/落后之分。集中执行的优势是职责集中、组件更专注计算，
框架便于统一排序、统计、旁路和错误处理。自主续调的优势是组件能直接表达
本次调用中的条件、重复交付和下游嵌套，但要支付调用契约、观测时机和可视化的成本。
集中执行也可以支持复杂控制流，只是需要明确的执行模型，而不是靠普通数据线自动获得。

### 11.3 从实际改造中得到的经验

1. **数据关系、配置关系、执行关系必须分别可解释。**
   有连线不必然有处理调用；没有数据端口也不代表组件没有 `process`。
   可执行节点的处理函数存在于底层，不等于画布已清楚表达其执行入口。
2. **不能靠音频/非音频推断调用语义。**
   音频端口可能截断传播；计算用数组可以传播驱动；标量/数组参数线只交付参数，
   不因数据类型相同就等同于计算数据线。非音频组件同样需要明确执行契约。
3. **“允许传播”和“这条线最终承担调用”不是一回事。**
   两端端口声明、目标独立入口和连接阻断共同决定有效关系；
   驱动归属圆点只表静态可达性，不足以说明调用路径或本拍是否实际执行。
4. **后续可视化应揭示契约，而不是要求用户猜源码。**
   展示接口角色、传播/截断属性、最终有效调用关系及不传播原因；
   静态调用关系与实时执行记录分开。采用现有线标记、执行流视图还是独立接口，
   尚需单独设计，不默认恢复一整套逐段手连的执行引脚。
5. **统一 wrapper 不能代替清楚的执行模型。**
   它能集中拦截调用，却不能让隐藏的续调时机自动变得可理解；
   “调用返回”和“输出尚未被下游改写”也并非同一时刻。
6. **实践揭示的成本应反过来校准设计，而不是维护既定路线。**
   此次只有走到组件实现、图形表达、旁路和统计推演，才具体看到集中执行的价值。
   后续架构取舍应比较用户可理解性、组件责任、控制流表达、测试成本和实测开销，
   不能把“链式”本身当成目标或优越性证明。

本次只记录对比和经验。现有组件自主续调原则不变；
若以后调整执行权归属，应作为独立架构决策评估，不混入 wrapper 实施。
