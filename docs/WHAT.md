# Orpheus — 做什么（WHAT）

> 本文回答：Orpheus 是什么、为谁而建、必须交付哪些能力、边界在哪里、怎样才算成功。它是后续技术方案与开发排期的需求基准。

---

## 1. 产品愿景

Orpheus 是一套面向音频 DSP 学习、算法实验、PC 实时处理与嵌入式部署的**可视化组件化音频框架**。

用户像搭积木一样，在图形界面上拖放组件、连接端口、配置参数、组织子系统；工程既能在 PC 上实时编译运行、听音调参、观察信号，也能一键生成完整、可读、可独立编译的 C/C++ 工程，用于传统 DSP、MCU 或 SoC 部署。

> 一句话定义：**“在电脑上像剪映一样直观地搭音频系统，生成的代码却像手工写的嵌入式模块一样干净可控。”**

---

## 2. 目标用户与核心场景

| 用户角色 | 典型场景 | 关键诉求 |
|---|---|---|
| DSP/音频算法学习者 | 理解滤波器、采样率、延迟、信号流 | 可视化、即时反馈、可查看源码与公式 |
| 算法研究员 | 快速验证 EQ、混响、分频、重采样等想法 | 参数调参、Probe 观测、可复现工程 |
| PC 音频爱好者 | 搭建自己的音效处理链路并分享给朋友 | 易用、可监听、可导出配置 |
| 嵌入式音频工程师 | 把验证好的算法部署到目标芯片 | 生成干净代码、固定内存、实时安全、可控 |
| 教师/课程作者 | 制作可交互的 DSP 实验课 | 教学视图、自动检查、版本可控 |

## 3. 核心能力（必须实现）

### 3.1 可视化音频系统编辑

- 通过图形界面添加、删除、复制、搜索组件节点。
- 类型化输入/输出端口，拖拽连线，连接合法性实时检查。
- 参数快速编辑与高级参数面板。
- 子系统（Subsystem）嵌套：结构型子系统可展开，封装型子系统可复用。
- 节点折叠、注释、模板、撤销/重做、自动保存。
- 工程文件为文本格式（YAML），便于 Git 版本管理。
- 中文优先的提示与错误信息。

### 3.2 组件化 DSP 基础库

首批必须支持的基础组件：

| 类别 | 组件 |
|---|---|
| 路由与增益 | Gain、Mute、Mixer、Split、Merge、Channel Mapper、Interleave、Deinterleave、Delay |
| 滤波器 | FIR、IIR、Biquad、Biquad Cascade、低通/高通/带通/陷波、DC Blocker、分频器 |
| 采样率与块处理 | 整数倍上/下采样、有理数重采样、Rebuffer、Block Splitter、Block Accumulator |
| 任务与桥接 | Task、Task Bridge、SPSC Ring Buffer、Ping-pong Buffer |
| 输入输出 | 音频设备输入/输出、WAV 文件输入/输出、测试信号生成器、通道监听 |
| 分析与调试 | Waveform Probe、RMS/Peak Probe、Spectrum Probe、CPU Meter、Buffer Level Probe、Memory Watch |

每个组件必须：

- 以独立可编译的 C/C++ 源文件或预编译库实现，对外暴露稳定 C ABI。
- 提供 `component.yaml` metadata，声明端口、参数、内存、延迟、实时安全属性。
- 在 PC 上可构建为动态库热加载，在目标工程上可静态编译或链接预编译库。
- 自带单元测试与 Golden Vector。
- 处理函数内不得动态分配内存、不得阻塞、不得访问 UI/通信设备。
- **支持嵌套组合**：组件可以是原子实现，也可以是内部包含 Graph 的复合组件；复合组件可逐层展开，也可封装复用。

### 3.3 实时 PC Runtime

- C/C++ Runtime 作为核心音频引擎，与 UI 完全解耦。
- 支持 Windows / Linux / macOS。
- 动态编译并加载组件动态库。
- 支持音频设备实时输入输出，以及 WAV 文件离线处理。
- 每路输入可独立注入，每路输出可监听。
- 实时参数更新、Probe 采集、性能统计。
- 支持工程热重载。

### 3.4 多任务与桥接

- 支持多个 Task，每个 Task 可独立设置：采样率、块长度、执行周期、优先级、核心归属、目标入口函数。
- 同任务内可存在不同采样率（通过重采样组件显式桥接）。
- 跨任务连接必须通过 Task Bridge 组件，视觉上体现为归属两个任务的算法链之间的连接。
- 桥接支持同步与异步场景，提供 Ring Buffer、Ping-pong Buffer、水位监控、欠载/溢出策略。
- 临界资源保护由 Runtime 框架提供，组件不自行实现线程同步。

### 3.5 端口与数据类型

组件端口按数据语义分为五类：

| 端口类型 | 用途 | 校验重点 |
|---|---|---|
| **Audio Port** | 连续音频块传输，参与节点连线 | 采样格式、通道数、采样率、块长度、时钟域 |
| **Control Port — Setting** | 运行时参数设置（Gain、Mute、EQ 参数等） | 类型、范围、更新策略、事务边界 |
| **Control Port — Command** | 一次性控制指令（Reset、Bypass、切换 Preset 等） | 命令 ID、参数、执行确认 |
| **Bulk Port** | 大块调音数据（FIR 系数、查找表、校准数据） | 长度、校验、双 Bank 原子提交 |
| **Debug Port** | Probe、日志、性能计数，可丢弃 | 不阻塞实时线程 |

**可变签名支持**：通用音频组件的端口签名（通道数、格式等）可由参数决定。图编译器根据节点参数实例值解析出确定性签名，再执行连接合法性校验。影响签名的参数变更需要重新编译执行计划。

### 3.6 统一控制中间层

- UI 不直接操控 Runtime 内存或目标内存；所有控制通过统一控制协议进行。
- 同一套控制接口可连接：本地 PC Runtime、独立 Runtime 进程、正式部署目标（通过外部 Transport）。
- 支持参数读写（Setting）、命令执行（Command）、批量事务、读回、状态查询、生命周期控制、Probe 配置、错误反馈。
- 通信实现由外部模块提供，核心框架只定义协议与 Transport 接口。

### 3.7 调音数据与实时控制双通路

| 通路 | 用途 | 关键特性 |
|---|---|---|
| 大块调音数据（Bulk） | FIR 系数、查找表、Preset、校准数据 | 连续内存、分块传输、校验、双 Bank 原子提交、失败回滚 |
| 实时控制数据（Control） | Gain、Mute、EQ 参数、开关 | 立即/块边界/平滑更新、多参数事务、生效反馈 |

### 3.8 代码生成

- 工程可生成完整、可读、可编译的 C/C++ 工程（CMake）。
- 生成策略为“组件源码复制 + 桥接代码生成”，不把框架复杂度叠加到生成代码。
- 生成内容包含：组件实例、Buffer、状态内存、任务入口、控制注册表、Probe 注册表、内存/延迟/执行报告。
- 生成工程不依赖 Python Runtime，可独立在 PC 或目标平台编译。
- PC 动态运行结果与生成工程运行结果须满足一致性误差标准。

### 3.9 非音频组件支持

- 允许“非音频组件”存在，例如 API 适配、内存调试、统计上报等。
- 非音频组件不实现具体通信；通信由外部模块通过统一控制协议或 Transport 完成。
- Probe 机制在生成代码中同样可用，用于真实目标调试。

### 3.10 教学支持

- 提供教学视图、工程视图、调试视图三种工作视图。
- 支持课程包：初始工程、目标状态、步骤说明、自动检查、教师答案。
- 学习者可以“听见现象 → 观察信号 → 调整参数 → 理解结构 → 查看公式 → 阅读实现 → 生成代码 → 部署运行”。

## 4. 非目标与边界（明确不做）

| 不做 | 原因 |
|---|---|
| 内置通信协议实现（TCP/UART/USB 等） | 通信由外部 Transport 实现，核心只定义接口 |
| 通用 MIDI/OSC 宿主 | 超出核心音频处理框架范围，可作为外部 Transport |
| 浮点/定点自动转换 | 目标 Profile 声明格式，组件按声明实现 |
| 自动 DSP 算法设计/优化 | 用户自行设计算法，框架负责装配与执行 |
| 商用级 DAW 功能（多轨录音、非线性编辑） | 聚焦实时处理与嵌入式生成 |
| 云端协作/账户系统 | 工程文件文本化，由 Git 等工具管理 |

## 5. 成功标准

### 5.1 首个里程碑成功标准

实现最小闭环：

```
WAV Input → Gain → Biquad → WAV Output
```

同时满足：

1. 工程由 YAML 描述。
2. Gain 与 Biquad 为独立 C/C++ 组件，带 metadata。
3. Python 自动构建组件动态库。
4. C++ Runtime 动态加载并处理音频。
5. 参数通过统一控制协议修改，RMS Probe 通过统一控制协议读取。
6. 同一工程可生成独立 CMake 项目并编译运行。
7. 动态运行与生成项目输出满足一致性误差标准。
8. 全流程可由自动化测试执行。

### 5.2 最终产品成功标准

- 学习者能在 15 分钟内搭建第一个可听音的音频链路。
- 任意合法工程可在 PC 实时运行与生成代码之间保持数值一致。
- 生成代码可在无 Python 环境下独立编译部署。
- 跨任务桥接通过长时间稳定性测试。
- 所有基础组件具备单元测试、ABI 合规测试与 Golden Vector。
- 工程文件 diff 友好，适合版本控制。

## 6. 关键术语

- **Project**：用户工程顶层对象，保存图、组件依赖、Target Profile、运行配置等。
- **Graph**：组件实例及其连接关系。
- **Node**：组件在工程中的实例。
- **Component**：可复用处理单元，由 Manifest、源码/库、测试、文档组成。
- **Atomic Component**：原子组件，由 C/C++ 源码或二进制库直接实现。
- **Composite Component**：复合组件，内部包含 Graph，可展开或封装复用。
- **Source Package**：源码包，含可编译源码与 metadata。
- **Binary Package**：二进制包，含预编译库与 metadata。
- **Port**：组件接收或输出数据的接口（Audio / Control / Bulk / Debug）。
- **Parameterized Port**：签名（通道数、格式等）由参数决定的端口。
- **Task Domain**：由同一任务入口调度的节点集合。
- **Rate Domain**：具有相同采样率与时钟来源的处理区域。
- **Task Bridge**：跨任务连接组件，负责缓冲、同步、水位与欠载/溢出处理。
- **Probe**：非阻塞旁路观察机制，用于波形、频谱、性能、内存等。
- **Target Profile**：描述部署平台能力（CPU、内存、编译器、线程模型等）。
- **Bulk Transfer**：大块调音数据分块传输、校验、原子提交机制。
