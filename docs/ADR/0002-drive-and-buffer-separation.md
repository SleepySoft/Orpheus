# ADR-0002：驱动与数据交付分离

- 状态：已接受，历史补录
- 决策日期：2026-11-06（依据已有设计文档）
- 记录日期：2026-11-09
- 关联：[ADR-0001](0001-component-owned-continuation.md)、[ADR-0003](0003-declared-interfaces-and-host-audio.md)

## 背景与问题

把数据 Buffer 当作执行入口、在组块攒满后自动触发消费者，会混淆“有什么数据”
和“何时调用”。速率转换、缓冲水位与源分频需要独立表达，不能让数据就绪改变算法时序。

## 决策

驱动箭头指向组件本体，不使用音频端口表示执行接口。Task/source 分支声明
周期与相位，组件仍自行续调。数据 Buffer 只负责交付、存储和有效性。
写满、提交或水位变化不自动启动 Task，不由框架补跑、等待或修正节拍。

普通音频/计算 BULK 连接默认允许传播驱动；control/debug 默认不传播。
组件端口可用 `propagate_drive` 声明截断。显式入口优先，不从数据周期推测执行入口。
驱动域圆点只是静态可达性标记，不代表运行状态、会合或并发安全。

## 考虑过的替代方案

- Buffer 写满自动启动消费者：时序跟随交付变化，不符合独立 Task 驱动。
- 为每个算法绘制执行引脚：把调用入口误当作数据端口，增加操作混淆。
- 自动匹配生产/消费节拍：隐藏用户必须明确的调用与缓冲契约，拒绝采用。

## 影响与约束

宿主和用户负责在实际调用边界准备数据；缺失输入必须明确报告，不能伪造静音。
数据传播声明不提供跨线程同步；跨 Task 使用真实数据桥。
音频缓冲驱动源与纯任务驱动源是不同组合，纯宿主 Buffer 本身不是时钟源。

## 演进与落实
